# Архитектура

Из чего состоит Bohr, какими сущностями он оперирует, где проходят границы между его компонентами и
по каким правилам написан его код.

Соседние документы:
[`API.md`](./API.md) — контракты, форматы и пути данных ·
[`TESTING.md`](./TESTING.md) — тестовая пирамида ·
[`DETERMINISM.md`](./DETERMINISM.md) — карта источников недетерминизма ·
[`PLATFORMS.md`](./PLATFORMS.md) — требования к хосту и матрица системных вызовов.

## 0. Имя и неймспейсы

Проект, бинарник и префикс крейтов — `bohr`. Из этого выводится каждая остальная поверхность:

| Поверхность | Значение |
|---|---|
| Rust-крейты | `bohr-types`, `bohr-tape`, `bohr-kernel`, … |
| Бинарник | `bohr` (одна многокомандная программа: `bohr run` / `explore` / `replay` / `reduce`) |
| C ABI, префикс символов | `bohr_` (`bohr_assert_always`, `bohr_random_bytes`) |
| Заголовок C | `bohr_sdk.h` |
| Rust SDK | крейт `bohr-sdk` |
| Python SDK | дистрибутив `bohr-sdk`, модуль **`bohr_sdk`** — имя верхнего уровня `bohr` занято на PyPI посторонним пакетом, см. §0.1 |
| .NET SDK | пакет `Bohr.Sdk`, неймспейс `Bohr` |
| Go SDK | модуль `github.com/bohr-dev/bohr-sdk-go`, пакет `bohr` |
| Окружение | `BOHR_*` (`BOHR_SEED`, `BOHR_OUT`, `BOHR_SDK_OUTPUT`) |
| Расширения файлов | `.tape` — сырая лента энтропии, `.bohr` — самодостаточный пакет сценария |
| Коды ошибок | `BOHR-####`, плоский стабильный каталог ([`API.md`](./API.md) §8) |
| Домен | `bohr.sh` — регистрируется на запуске, перед v1.0, единственным публичным релизом |

Префикс символов `bohr_`, а не `b_`: символы SDK попадают в глобальное пространство имён чужого
процесса рядом с их собственными и десятками сторонних библиотек. Имя достаточно короткое, чтобы его
набирать, и достаточно специфичное, чтобы не столкнуться.

### 0.1 Доступность имён по факту проверки

Проверено 9 августа 2026. Две из шести поверхностей оказались заняты, и обе записаны здесь, чтобы к
рассуждению не возвращаться заново.

| Поверхность | Результат |
|---|---|
| crates.io `bohr`, `bohr-sdk`, `bohr-cli` | свободны |
| NuGet `Bohr`, `Bohr.Sdk` | свободны |
| Организация GitHub `bohr-dev` | свободна (`bohr` — пользовательский аккаунт с 2011 года, кандидатом никогда не был) |
| Дистрибутив PyPI `bohr-sdk` | свободен |
| **Модуль верхнего уровня PyPI `bohr`** | **занят** — посторонний дистрибутив `bohr` (0.2.77, последний релиз октябрь 2024) ставит пакет `bohr/` |
| **`bohr.dev`** | **занят** — живой личный блог, не припаркован и не продаётся |

**Поэтому Python-модуль называется `bohr_sdk`, а не `bohr`.** Два дистрибутива, ставящих
`bohr` верхним уровнем, сломали бы `import bohr` в зависимости от порядка `sys.path` — ровно тот
«конфликт версий внутри чужой сборки», ради предотвращения которого существует правило S3 в §9.
Называть модуль по имени дистрибутива — и без того обычная конвенция Python, а примеры читаются как
`import bohr_sdk as bohr`.

Домен переехал на `bohr.sh`, а не пошёл в переговоры за `bohr.dev`: запуск требует домена, а
переговоры без срока — не план. `.sh` вдобавок та зона, которую аудитория уже связывает с системным
инструментарием. Все адреса проекта (`security@`, `conduct@`) следуют за ним.

Всё остальное — имя проекта, бинарник, префикс крейтов, префикс символов C, неймспейс .NET — не
затронуто и остаётся `bohr`.



## 1. Языки и их роль

| Язык | Роль | Почему |
|---|---|---|
| **Rust** | Всё, что содержит логику: бинарник супервизора, бэкенды детерминизма, ядро (часы, планировщик, виртуальный мир), исследователь, сжиматель, генератор отчётов | Три причины сразу. (1) Это системный инструмент: он управляет `ptrace`, пишет программы seccomp-BPF, разбирает ELF и лезет в чужую память — пауза сборщика мусора в супервизоре была бы источником недетерминизма в том, чья единственная цель — детерминизм. (2) Аудитория, которой мы это продаём (базы данных, реализации консенсуса, инфраструктура), уже живёт в Rust; инструмент на их языке — это инструмент, который они прочитают и пропатчат. (3) Супервизору доверяют чужую сборку; безопасность памяти в доверенном компоненте — не роскошь. |
| **C** | Тестовые мишени в `testdata/`, заголовок C для SDK, шим для переписывания `RDRAND` | Чтобы доказать, что мы работаем с программами, которые не компилировали, нужны программы, которые мы не писали на Rust. Мишени на C — самый дешёвый способ точно воспроизвести враждебный путь через libc. |
| **Python** | SDK №2 плюс скрипты сравнения отчётов в CI | Вторая по величине популяция систем, которым мы полезны, — это сервисы и тестовые обвязки на Python. В рантайме Python нет — только в SDK и в склейке CI. |
| **C#** | SDK №3 | Намеренно. Угол .NET занят слабо (Coyote умеет только C# и почти не развивается), а корпоративная .NET-аудитория велика и платёжеспособна. |
| **Go** | SDK №4 | Самая большая популяция кода, уже размеченного SDK Antithesis. |
| **ассемблер (x86-64)** | Только фрагменты: трамплины `RDRAND`, заглушки эмуляции TSC, корпус тестов сканера инструкций | Больше ничего. Ассемблер несёт цену сопровождения, и его берётся ровно столько, сколько требуют перехватываемые инструкции. |
| **TypeScript / JS** | Не используется | HTML-отчёт генерируется как статическая разметка со встроенным CSS и парой сотен строк ванильного JS. Ни сборщика, ни фреймворка, ни `node_modules`. Причина — в §5.13. |

**Чего нет и не будет в v1:** любой рантаймовой зависимости от языка кроме Rust; демона; базы данных;
сетевого сервиса; контейнерного рантайма; Kubernetes. `bohr` — это один статически линкуемый
бинарник плюс необязательные пакеты SDK.

## 2. Три исполняемых контекста

Это главное деление всей системы. Всё остальное — детали внутри одного из трёх.

```
┌──────────────────────────────────────────────────────────────────────────┐
│ КОНТЕКСТ 1 · СУПЕРВИЗОР  (наш процесс, бинарник `bohr`)                  │
│                                                                          │
│   исследователь ──► ядро ──► бэкенд ──► ptrace/seccomp ──► задачи гостя  │
│      ▲                │                                                  │
│      └── след ◄───────┘   сжиматель · отчёты                             │
│                                                                          │
│  Держит ленту энтропии, логические часы, планировщик и весь виртуальный  │
│  мир. Единственный процесс, которому позволено принимать                 │
│  недетерминированное решение — и каждое он принимает выборкой из ленты.  │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ ptrace + seccomp + разделяемая память
               ┌────────────────┴──────────────────┐
               ▼                                   ▼
┌───────────────────────────────┐  ┌───────────────────────────────────────┐
│ КОНТЕКСТ 2 · ГОСТЬ            │  │ КОНТЕКСТ 3 · SDK (необязательный)     │
│ немодифицированная программа  │  │ bohr-sdk, слинкованный в гостя        │
│ клиента, один или больше      │  │                                       │
│ процессов                     │  │ Пишет записи утверждений и наблюдений │
│                               │  │ в дескриптор, выданный супервизором.  │
│ Думает, что говорит с Linux,  │  │ Берёт случайность из ленты, а не из   │
│ сетью и диском. Говорит с     │  │ системы. Вне Bohr каждый вызов —      │
│ нами. Не меняется, не         │  │ пустышка.                             │
│ пересобирается.               │  │                                       │
└───────────────────────────────┘  └───────────────────────────────────────┘
```

Правило, из которого растёт всё остальное: **гость никогда не узнаёт, что его симулируют, иначе как
через SDK, а SDK необязателен.** Два следствия, которых мы держимся:

1. Каждая возможность обязана быть полезной при **отсутствующем контексте 3**. Падения, зависания,
   повреждение данных и провалы утверждений внутри гостя находятся без всякой разметки. SDK
   добавляет к найденному; он не предусловие.
2. Супервизор никогда не доверяет гостю. Гость, вернувший мусор по каналу SDK, порождает диагностику,
   а не падение супервизора: гость — ровно то, что мы ожидаем сломанным.

### Режим симуляции против режима воспроизведения

| | `bohr run` / `bohr explore` | `bohr replay` |
|---|---|---|
| Откуда лента | сид → лента, затем мутация | читается дословно из пакета |
| Политика планирования | `random`, `pct`, `adversarial` | `replay` — решения выводятся из той же ленты |
| Инъекция сбоев | активна, выбирает исследователь | воспроизводится точно |
| Сбор покрытия | включён | по умолчанию выключен (он ничего не искажает, но стоит) |
| Критерий успеха | свойство нарушено / покрытие выросло | **отпечаток следа равен записанному** |

Оба режима — это **то же** ядро и **тот же** бэкенд. Различаются лишь источник байт и то,
сравнивается отпечаток или записывается. Движков **не** два: движок воспроизведения, расходящийся с
движком исследования, разрушил бы гарантию, на которой держатся оба режима.

### Граф зависимостей крейтов

Ациклический и намеренно узкий. Стрелка означает «знает о».

```
                              bohr-types
        ┌──────────────┬───────────┼────────────────────┐
        ▼              ▼           ▼                    ▼
   bohr-tape      bohr-trace   bohr-backend       bohr-sdk-proto
        │              │        ▲          ▲            │
        └──────┬───────┘        │          │            │
               ▼                │          │            │
          bohr-kernel      bohr-backend-  bohr-backend- │
   объявляет порты:            ptrace          null     │
   WorldModel · Oracle                                  │
   SchedulePolicy                                       │
      ▲     ▲      ▲     ▲          ▲                   │
      │     │      │     └──────────┼──────┐            │
 bohr-world │  bohr-reducer         │  bohr-report ◄────┘
 (модель)   │                       │
      bohr-explorer            bohr-testkit
                            (фикстуры и стенд
                              детерминизма)

                        всё вышеперечисленное ────► bohr-cli
```

Направление вокруг `bohr-kernel` — то, на что стоит смотреть: **это от ядра зависит мир, а не
наоборот.** Ядро
объявляет порты и крутит их; модель распределённых систем, бэкенды, исследователь и сжиматель
подключаются. `bohr-cli` — единственное место, где выбирается и связывается по одной реализации
каждого.

Что здесь важно:

- **`bohr-kernel` не зависит ни от одной реализации бэкенда.** Он зависит только от крейта-трейта
  `bohr-backend`. Перехватчик — двигатель, а
  двигатель сменный. Сборка происходит ровно один раз, в `bohr-cli`. Проверяется механически в CI
  (§8, правило 14).
- **`bohr-kernel` не зависит и ни от одной модели мира** (§5.16). `WorldModel`, `Oracle` и
  `SchedulePolicy` объявлены в ядре и реализованы вне его. `bohr-world` — это *одна* модель, для
  распределённых систем, а вторая предметная область добавляет соседний крейт, а не правит этот. В CI
  та же проверка, что и для бэкенда.
- **`bohr-tape` не знает, что значит выборка.** Он выдаёт байты и записывает смещения. Семантика
  («эта выборка выбрала следующую задачу», «эта решила потерять пакет») живёт в ядре и привязывается
  к *журналу выборок*, который является артефактом прогона — см. §5.3. Если в крейте ленты когда-нибудь
  появится `fn draw_packet_loss`, слоистость сломана.
- **`bohr-explorer` и `bohr-reducer` — братья, а не цепочка.** Ни один из них ничего не исполняет:
  оба — конечные автоматы, которые предлагают работу и которым передают результаты (§5.19). Сжиматель
  обязан работать самостоятельно над пакетом, снятым месяц назад другой версией исследователя.
- **`bohr-backend-null` существует по практической причине, а не из чистоплюйства.** Двое инженеров
  не могут оба быть заблокированы на работе с системными вызовами Linux. С null-бэкендом слои 2–4
  имеют полноскоростные модульные и свойственные тесты на любой машине разработчика, а CI гоняет их
  секунды вместо минут ([`TESTING.md`](./TESTING.md) §4).
- `bohr-types` не зависит ни от чего нашего и почти ни от чего чужого (`serde`, `blake3`). Он
  компилируется и в путь SDK, где каждая транзитивная зависимость — это обязательство внутри чужой
  сборки.

## 4. Домейн-модель

Точные сигнатуры, форматы и правила версионирования — в [`API.md`](./API.md). Этот раздел определяет
сущности и их инварианты.

### 4.1 Лента энтропии — идея, из которой вытекает всё остальное

**Весь прогон управляется одной строкой байт.** Каждый раз, когда системе надо принять
недетерминированное решение, она **откусывает** байты от ленты:

какая задача пойдёт следующей · потерять этот пакет или нет · насколько задержать доставку · порвать
эту запись при падении или нет · что вернуть на `getrandom` · убить ли сейчас узел 3.

Из одного этого решения падает пять свойств, и именно поэтому оно лежит в фундаменте с первого дня:

| Свойство | Следствие |
|---|---|
| сид → лента → прогон | одно 64-битное число полностью задаёт мир; дёшево хранить, дёшево пересылать |
| поиск = мутация ленты | мутаторы AFL++/libFuzzer применимы напрямую; зрелый пласт инженерии, который мы не пишем |
| покрытие направляет поиск | классическая петля фаззинга работает без изменений |
| сжатие = минимизация ленты | дельта-отладка работает над обычным списком байт |
| воспроизведение = та же лента | файл сценария — это лента, отпечатки и конфиг, и больше ничего |

**Структура.** Лента — конечный **префикс**, за которым идёт детерминированное
**расширение**:

```
лента = байты префикса (материал корпуса, мутируется исследователем)  ‖  ChaCha8(сид, счётчик) …
```

Расширение существует потому, что прогон не может знать заранее, сколько решений он примет. Гость,
который прокрутился дольше ожидаемого, не имеет права упасть с «лента кончилась»; он обязан
продолжать выбирать, и полученные байты обязаны остаться чистой функцией сида. Граница между
префиксом и расширением записывается в след, но невидима для кода, делающего выборку.

**Выборки типизованы.** `draw_u64`, `draw_range(n)`, `draw_bool(p)`, `draw_into(out)`,
`draw_weighted(&weights)`. Отображение байт в значение — описанная и замороженная функция
([`API.md`](./API.md) §2.4): её изменение обесценивает каждый сохранённый пакет, поэтому она
версионируется.

**Журнал выборок — артефакт прогона, а не часть ленты.** По ходу прогона ядро записывает для каждой
выборки кортеж `(смещение в ленте, длина, идентификатор площадки, решение)`. Журнал — это то, что
делает сжиматель структурно осведомлённым, а отчёт читаемым, — но он **производный**, никогда не
вход. Именно это разделение даёт нам одновременно побайтовые мутаторы и структурное сжатие; оно
записано как §5.3.

### 4.2 Логическое время

`Tick` — это `u64` **виртуальных наносекунд**. Оно не связано с настенным временем и никогда не
читается с хоста.

- Время продвигается только в определённых точках: граница системного вызова, переключение
  планировщика, исчерпание бюджета инструкций, явное истечение таймера в виртуальном мире.
- Гость, спящий час, просыпается мгновенно, продвинув `Tick` на 3.6e12.
- **У каждого узла свои часы** с настраиваемым смещением и скоростью ухода относительно часов мира.
  Рассинхрон часов между узлами — один из богатейших источников багов в распределённых системах, а
  моделирование стоит нам одного `i64` и одной рациональной дроби на узел.
- Прогресс внутри потока, где нужна мера точнее чем «один системный вызов», измеряется числом
  выполненных условных переходов, читаемым из аппаратного счётчика — приём `rr`. Это **измерение**
  прогресса, а не источник времени: значение счётчика превращается в детерминированную дельту тактов
  замороженной формулой, а если счётчик недоступен, мы откатываемся на счёт системных вызовов и
  сообщаем об этом в заголовке прогона.

### 4.3 Миры, узлы и задачи

- **`World`** — всё, что содержит прогон: набор узлов, виртуальная сеть, часы мира, курсор ленты.
  Ровно один на прогон.
- **`Node`** — симулируемая машина. Владеет виртуальным диском, сетевой идентичностью, своими часами
  и жизненным циклом (`Running`, `Frozen`, `Dead`, `Restarting`). Узел отображается в один или
  несколько процессов гостя.
- **`Task`** — единица исполнения, которую выбирает планировщик: один поток гостя. `TaskId`
  **виртуален** и назначается нами в порядке создания; хостовый tid специфичен для машины и в след не
  попадает никогда.
- **`Fd`** — виртуальный файловый дескриптор. Числовой дескриптор гостя транслируется на границе.
  Номер дескриптора у гостя стабилен только потому, что мы делаем его стабильным.

Виртуальные идентификаторы существуют по одной причине: **любое число хостового происхождения,
попавшее в след, разрушает межмашинную воспроизводимость** (цель T4 — тот же пакет обязан
воспроизводиться на другой машине). Поэтому pid, tid, номера inode, адреса и номера дескрипторов
виртуализованы, и есть проверка CI, что ни один сырой хостовый идентификатор не сериализуется в след.

### 4.4 События и след

- **`Event`** — один записанный факт: системный вызов начался или вернулся, решение планировщика,
  пакет отправлен, доставлен или потерян, сработал сбой, вычислено утверждение SDK, умер узел. Несёт
  `EventId` (монотонный счётчик в пределах прогона), `Tick`, `NodeId`, `TaskId` и типизованную
  нагрузку.
- **`Trace`** — упорядоченный поток событий прогона. Только на дозапись, потоком на диск, никогда
  целиком в памяти: прогон может дать десятки миллионов событий, и супервизор не имеет права быть
  тем, у кого кончилась память.
- **`TraceDigest`** — `blake3` от **канонической** проекции потока событий. Каноническая проекция
  намеренно исключает всё хостоспецифичное (длительности, хостовые pid, адреса хостового
  происхождения). **Отпечаток и есть определение «того же прогона».** Цель T1 — 1000 прогонов одного
  сида дают побайтово одинаковый след — механически проверяется как «1000 одинаковых отпечатков», а
  не сравнением файлов.

**Прогон сохраняет свою ленту, а не свой след.** След — чистая функция ленты, конфигурации и
бинарей, поэтому хранить его значит хранить кэш детерминированного вычисления. Обычный прогон
оставляет ленту, карту покрытия и счётчики — килобайты. Находка оставляет целый пакет. Прогон,
который потом захотели посмотреть, воссоздаётся воспроизведением. Сам поиск след никогда не читает:
его ведут карта покрытия, класс находки и несколько счётчиков.

### 4.5 Сбои

**`Fault`** — это намеренная злоба, применяемая миром в момент, выбранный из ленты. Каталог закрыт;
добавление варианта — минорная версия формата пакета.

| Семейство | Варианты |
|---|---|
| Сеть | задержка, потеря, дублирование, перестановка, разрыв (в том числе **односторонний**), серая деградация |
| Диск | рваная запись, задержка синхронизации, `ENOSPC`, `EIO`, потеря незафиксированных данных при падении |
| Узел | убийство (аналог `SIGKILL`), заморозка и разморозка (пауза сборщика мусора, перегрузка), чистый перезапуск, перезапуск со старого снимка диска, отмотка набора узлов к общему предку |

Односторонний разрыв назван отдельно, потому что это случай, который команды чаще всего не тестируют,
и он же надёжнее всего ломает реализации консенсуса.

**Часы разведены, а не сломаны.** Каждый узел до старта вытягивает собственное смещение и скорость
ухода (§4.2), поэтому два узла никогда не согласны о времени, а прогон, где они согласны, не дошёл бы
до дефектов, которые на этом несогласии держатся. Чего нет — так это сбоя, который сдвигает или
переуводит часы **во время** прогона, и здесь он назван отсутствующим, а не оставлен на обнаружение
сценарием, который не может его попросить.

**Каталог — это обещание, и он привязан к коду.** Каждая модель объявляет сбои, которые умеет
вносить, а `scripts/lint-rules.sh` сверяет это объявление с каждым сбоем, который модель на самом
деле рассказывает. Это два отдельных списка, которых во время работы не читает ничто, поэтому они
расходятся; кампания планирует покрытие по объявлению, и именно это делает расхождение дорогим.

**Целеуказание сбоев.** Сбои не вставляются равномерно случайно. Исследователь предпочитает моменты,
**семантически опасные** — сразу после записи и до её подтверждения, во время передачи лидерства, в
середине двухфазной фиксации. Эти моменты определяются по вызовам `fault_point` из SDK, когда он
есть, и по эвристикам формы системных вызовов, когда его нет ([`API.md`](./API.md) §5.4).

### 4.6 Свойства

Свойства приходят из SDK (контекст 3) и от самого супервизора.

| Свойство | Смысл | Нарушено, когда |
|---|---|---|
| `always(cond, name)` | обязано выполняться при каждой проверке | любая проверка ложна |
| `always_or_unreachable(cond, name)` | выполняется всякий раз, когда сюда дошли | дошли и ложно |
| `sometimes(cond, name)` | обязано быть истинно хотя бы раз **за всю кампанию** | кампания закончилась с нулём истинных проверок |
| `reachable(name)` | обязано быть достигнуто хотя бы раз за кампанию | ни разу не достигнуто |
| `unreachable(name)` | не должно быть достигнуто никогда | достигнуто хоть раз |

`sometimes` и `reachable` работают **на уровне кампании**, а не прогона, и именно это делает их
ценными. Они не находят падений — они дают **карту непроверенного** («за десять миллионов прогонов мы
ни разу не попали в смену лидера при полном диске»). Эта карта превращает инструмент из искалки багов
в аргумент о покрытии, и это та половина SDK, которую недооценивают.

По кампании они складываются сливаемым счётчиком в каталоге корпуса: на свойство —
`{evaluations, true_count, first_true_run_id}`, слияние — сложением счётчиков и выбором более раннего
прогона. Именно сложение делает ответ независимым от порядка, в котором заканчивают воркеры, а это и
позволяет `-j 1` и `-j 8` согласовываться (§6.2). Счётчик живёт в корпусе, потому что корпус — это то,
что кампания несёт с собой при возобновлении или переносе, и потому что пересчитывать не из чего:
удовлетворённый `sometimes` не даёт находки, а неудовлетворённый не даёт вообще ничего.

Свойства со стороны супервизора не требуют разметки вообще: падение гостя, зависание (нет прогресса в
пределах бюджета тактов), неподдержанный системный вызов, повреждение памяти, о котором сообщили
собственные санитайзеры гостя, и ненулевой код выхода.

### 4.7 Пакет сценария

Файл `.bohr` — это продукт. Он **самодостаточен** и **машинонезависим**:

манифест (версия формата, версия инструмента, конфиг, сид) · префикс ленты · отпечатки бинарников
каждого исполняемого объекта, который отобразил гость · профиль хоста, который был *предъявлен* гостю
(фиксированные листы CPUID, строка версии ядра) · журнал событий · записи SDK · журнал выборок ·
карта покрытия.

Отпечатки существуют, чтобы `bohr replay` на другой машине либо воспроизвёл точно, либо отказался с
точной причиной («libc.so.6 отличается: записано `blake3:ab12…`, найдено `blake3:cd34…`»). Молча
воспроизвести против другого бинарника и сообщить «не воспроизводится» было бы самым разрушительным
режимом отказа этого инструмента, потому что это научило бы пользователей ему не доверять.

## 5. Инварианты

Двадцать свойств, которые выполняются во всей системе и на которых построено всё остальное. Каждое
говорит, что имеет место, чего это системе стоит и — там, где проверку делает машина, — где эта
проверка живёт. На них ссылаются из исходников по номеру (`§5.7`).

### 5.1. Лента — единственный источник недетерминизма

Ни один компонент не принимает недетерминированное решение иначе, чем выборкой из ленты. Нет
`rand::thread_rng()`, нет `Instant::now()`, нет `SystemTime::now()`, нет порядка обхода `HashMap` ни
на одном пути, влияющем на решение, и нет `std::thread` в цикле принятия решений.

Каждое место принятия решения протянуто до курсора, а значит `&mut TapeCursor` передаётся далеко
вниз. Окружающий генератор избавил бы от этого неудобства — и заодно избавил бы от детерминизма, не
изменив ни одного места вызова.

**Проверяется** файлом `clippy.toml`, который запрещает эти методы и типы на этапе компиляции, и
`scripts/lint-rules.sh` для остального (§8, правило 14).

### 5.2. Граница бэкенда не протекает

`bohr-backend` говорит в терминах операций гостя: «задача T остановилась на входе в системный вызов с
такими аргументами», «возобновить T с подставленным возвращаемым значением», «T отказала на `CPUID`».
Он никогда не упоминает ptrace, `waitpid`, seccomp, сигналы или `/proc`. Ничто выше границы не
разбирает, какой бэкенд используется.

Часть бэкенд-специфичных оптимизаций поэтому недостижима через интерфейс — например слитая операция
«прочитать регистры и память за одну остановку». Там, где замер показывает, что это важно, граница
получает пакетную операцию под флагом возможности, а не течь.

**Проверяется** файлом `scripts/lint-rules.sh`: `ptrace|seccomp|waitpid|libc::` не встречается ни в
одном крейте, кроме `bohr-backend-ptrace`, и ни одна реализация бэкенда не входит в дерево
зависимостей `bohr-kernel`.

### 5.3. Лента плоская, журнал структурный

Лента — байты. Журнал — структура (§4.1). Два иначе несовместимых требования выполняются
одновременно: к ленте применимы готовые байтовые мутаторы, а редуктор и отчёт читают журнал.

Структурная лента — список типизованных записей — сделала бы мутацию семантически осведомлённой и
ломала бы каждую сохранённую запись корпуса при первом же изменении набора мест принятия решений.
Плоская лента без журнала оставила бы редуктор слепым, а отчёт нечитаемым. Разделение стоит одного
вектора на прогон.

Журнал восстановим, и именно это делает безопасным его производность: `bohr replay` выводит его
заново, а не читает, и сохранённый журнал, расходящийся с выведенным, — жёсткая ошибка, потому что
это значит, что ABI выборок изменился под сохранённым пакетом.

### 5.4. В каждый момент исполняется одна задача

Планировщик даёт исключительное право исполнения ровно одной задаче. Конкурентность моделируется
чередованием, а не параллелизмом, и именно это делает гонки данных воспроизводимыми.

**Ограничение.** Настоящие многоядерные эффекты модели памяти — буферизация записей, слабое
упорядочивание — не воспроизводятся. На x86-64 с TSO это теряет меньше, чем потеряло бы в другом
месте, и записано в «вне области» (§13), а не мелким шрифтом. Программе, дефект которой требует
настоящего параллелизма, нужен инструмент, моделирующий модель памяти, — например `loom`.

Пропускная способность по реальному времени поэтому одноядерная. Несколько ядер используются
запуском независимых сидов параллельно, что тривиально параллелится (§6.2).

### 5.5. Время логическое и никогда не хозяйское

`Tick` — виртуальные наносекунды (§4.2), читаемые из мира и никогда из машины. Пропуск хозяйских
часов внутрь, при всей их монотонности, сломал бы цель T1 на первом же прогоне, где таймаут сработал
в другой точке.

**Следствие для того, что можно тестировать.** Любой таймаут в госте мгновенен, поэтому гость,
крутящий цикл на стенных часах в ожидании реально прошедшего времени, будет крутиться. Этот
образец — повторяющиеся чтения часов без других системных вызовов — распознаётся и сообщается как
диагностируемое состояние, а не оставляется висеть.

### 5.6. Фильтр seccomp-BPF решает, ради чего стоит останавливаться

Голый `ptrace` останавливается дважды на каждый системный вызов. Фильтр seccomp-BPF, установленный в
госте, решает в ядре, какие вызовы интересны: `SECCOMP_RET_TRACE` для них, `SECCOMP_RET_ALLOW` для
остальных. Цель T3 (≤5× native) без него недостижима, а сама техника — та, что дала `rr` примерно
стократное ускорение на микробенчмарках.

Фильтр — скомпилированная BPF-программа, обязанная согласовываться с таблицей обработчиков. Оба
порождаются из одной таблицы (`bohr-backend-ptrace/src/linux/syscalls.rs`), потому что вызов, который
обработан, но не трассируется, — дыра в детерминизме, которую ничто ниже по потоку не обнаружит.

**Проверяется** тестом, утверждающим, что фильтр трассирует ровно тот набор, который реализует
таблица.

### 5.7. Немоделируемый системный вызов громко заканчивает прогон

Системный вызов, который мир не моделирует, не пропускается на хост и не заглушается `ENOSYS`. Он
заканчивает прогон с `BOHR-2001`, называя номер вызова и вызывающую задачу.

Выносимым это делает дисциплина области: поддерживается то, что нужно текущим целям охоты, по отчёту
«видели вызов, но не обрабатываем». Абстрактная полнота не цель; ранжированный список, выведенный из
настоящих целей, — цель. Первый прогон против новой программы поэтому скорее всего закончится именно
так, и это сделано дёшево: ошибка называет вызов и ссылается на таблицу, а `bohr survey -- ./x`
сообщает весь неподдерживаемый набор сразу, а не по одной записи за прогон.

**Обзор отвечает на то, что не может смоделировать; прогон отказывает.** Это разные команды, а не
одна команда с флагом, потому что флаг рано или поздно оказывается включён в чьей-то непрерывной
интеграции, и прогон, заглушивший половину своих вызовов, выносит вердикт. Разделёнными их потом
держит не флаг, а мир: обозревающий мир несёт собственную идентичность, поэтому всё, что он произвёл,
отвергается проверкой происхождения до того, как это можно воспроизвести как прогон.

**Моделируемый вызов с невозможными аргументами получает ответ, а не исполнение.** Гость сам называет
длины, смещения и адреса. Файл, который вырос бы за пределы хранимого, — это `EFBIG`, адрес,
заворачивающий адресное пространство, — `EFAULT`, а передача больше границы выполняется до границы и
сообщается короткой. Супервизор — единственный компонент, чей отказ уничтожает свидетельство, ради
которого прогон существует, а гость, просящий абсурдного, обычно не враждебный, а программа в
процессе поломки — то есть ровно тот случай, когда свидетельство и важно.

### 5.8. `RDRAND` — дыра, и она задокументирована как дыра

Процессор не даёт способа перехватить `RDRAND`/`RDSEED`. Делается четыре вещи и не заявляется
большего: гасится бит возможности в CPUID, чтобы большинство библиотек ушло на запасной путь; в
исполняемых сегментах объекта ищутся опкоды `0F C7 /6` и `0F C7 /7`; найденные адреса сообщаются
предупреждением; и с `--patch-rdrand` гость получает подготовленные файлы, где эти инструкции
заменены.

**Найти и заменить — разные вопросы, и ответы у них разные.** Поиск идёт по двум байтам и находит
все настоящие инструкции и вдобавок часть смещений. **Сообщается** всё найденное: место, которое
есть и о котором не сказали, — это дыра, выданная за твёрдую землю. **Заменяется** только то, что
установила развёртка: инструкции измеряются от символа функции, а там, где объект не хранит
покрывающего символа — раздетая разделяемая библиотека экспортирует немногое, — несколькими
развёртками с разных байтов перед кандидатом, сошедшимися на одном. Запись поверх байтов,
оказавшихся серединой другой инструкции, портит её молча, поэтому кандидат, которого никто не
установил, сообщается и не трогается.

Замена той же длины, что и заменяемое: `rdrand r32` — три байта, `xor r, r` с `stc` — тоже три.
Ничто не сдвигается, а гость получает ноль и сообщение, что чтение удалось, — это обрабатывает
всякий вызывающий, потому что настоящая инструкция вправе не сработать. Ноль слабее розыгрыша с
ленты и сильнее всего, что доступно без ловушки.

Прогон никогда не числится детерминированным, пока в отображённой странице сидит необезвреженный
`RDRAND`.

### 5.9. Пакет самодостаточен и отказывается лгать

Пакет несёт отпечатки всего, что гость отобразил (§4.7), и `bohr replay` проверяет их до запуска.
Расхождение — ошибка, называющая конкретное различие, а не предупреждение.

Пакеты поэтому воспроизводимы только против тех же самых бинарей. `bohr replay --binaries <dir>`
существует, чтобы читатель мог указать на нужную сборку, и записывается достаточно, чтобы её достать;
проверка не ослабляется.

### 5.10. Покрытие — оптимизация, и его отсутствие деградирует мягко

Три уровня в порядке предпочтения: `-fsanitize-coverage=trace-pc-guard` через разделяемую память для
гостей, которые можно пересобрать; Intel PT там, где хост его поддерживает; маркеры от SDK в
остальных случаях. Без всех трёх исследователь откатывается на случайную мутацию и планирование PCT —
и говорит об этом.

Утверждение «никаких изменений в коде» поэтому точно для *поиска* дефектов и слабее для
*эффективности* поиска. Уровни названы в README прямо, а не выданы за однородные.

### 5.11. Ядро не делает ввода-вывода и системных вызовов

`bohr-kernel`, `bohr-world`, `bohr-explorer` и `bohr-reducer` — конечные автоматы над
`(лента, события)`. Весь контакт с операционной системой происходит в `bohr-backend-ptrace`,
`bohr-trace` (запись файлов) и `bohr-cli`.

Что это даёт: тест «однонаправленное разделение между узлами 2 и 3 на тике 40 000 приводит к выбору
двух лидеров» выполняется за микросекунды, на любой операционной системе, без привилегий. Модель
мира, которой нужен настоящий сокет, превратила бы его в медленный интеграционный тест, и набор
держал бы десять таких, а не тысячу.

### 5.12. `unsafe` живёт ровно в одном крейте

`#![forbid(unsafe_code)]` в каждом крейте, кроме `bohr-backend-ptrace` и FFI-обёрток SDK для C и C#.
В этом крейте каждый блок `unsafe` несёт комментарий `// SAFETY:`, называющий инвариант, который
обязан обеспечить вызывающий.

Супервизор запускают поверх чьей-то продакшн-сборки. «Небезопасная поверхность — один крейт, вот
он» — проверяемое утверждение; «unsafe разбросан по четырнадцати крейтам» — нет.

**Проверяется** файлом `scripts/lint-rules.sh`.

### 5.13. Отчёт — один статический HTML-файл

`bohr report` выдаёт один `.html` со встроенным CSS и обычным JavaScript. Никакого сервера,
фреймворка, шага сборки, `node_modules` и CDN. Он открывается с файловой системы, прикладывается к
письму, кладётся в issue и коммитится в репозиторий.

Это структурное решение, а не косметическое: отчёт, который для просмотра требует `npm install`, не
будет приложен к баг-репорту тем мейнтейнером, которого он должен убедить, а отчёт за сервисом
умирает вместе с сервисом. Визуализация написана вручную — несколько сотен строк JavaScript без
зависимостей.

**Потолок — четыре мегабайта**, столько принимает трекер задач и столько открывается без ожидания.
Прогон, слишком длинный, чтобы отрисоваться в этих пределах, не обрезается, а окном: окрестность
отказа плюс каждый сбой, обещание и смена состояния узла, где бы они ни оказались, а остальное
записывается рядом со страницей как JSON Lines. Неотрисованное посчитано на странице, потому что
дыра, показанная как ничто, читается как прогон, в котором ничего не произошло.

### 5.14. Формат записей SDK — внешний контракт

SDK читают и пишут те же локальные JSON-записи, что пишут SDK Antithesis при запуске вне их среды
(`ANTITHESIS_SDK_LOCAL_OUTPUT`), поэтому команда, уже размеченная под Antithesis, работает под Bohr
без правок.

Схема поэтому не наша, чтобы её менять. `bohr-sdk-proto` считает совместимое подмножество замороженным
и кладёт каждое собственное расширение под ключ со своим пространством имён, так что запись, сделанная
здесь, остаётся читаемой их инструментами и наоборот. Сдвиг с их стороны ловится тестом совместимости
против сохранённых фикстур, а не угадыванием.

### 5.15. Движок тестируется под собой

Ядро, планировщик и виртуальный мир запускаются под собой, а гейт детерминизма выполняется на каждом
коммите ([`TESTING.md`](./TESTING.md) §7). У инструмента, находящего дефекты в чужой конкурентности,
нет оснований, если его собственная не проверена.

**Мигающий тест в этом репозитории — дефект уровня P1, а не аннотация повтора.** Пометить тест
`#[ignore]`, потому что он «иногда красный», — это написать обвинение против себя.

### 5.16. Мир — порт, как и бэкенд

`bohr-kernel` владеет временем, планированием и лентой. Он не владеет моделью среды. Сеть, диск,
жизненный цикл узла и каталог сбоев живут за трейтом `WorldModel` ровно так же, как перехват живёт за
`DeterminismBackend` (§5.2). Ядро приводит мир в движение; какой именно — оно не знает.

```rust
/// Среда, в которой гость считает, что он исполняется.
///
/// Ядро поставляет остановки, часы и курсор ленты; модель решает, что мир с ними делает.
/// Реализации доменно-специфичны по замыслу: модель распределённых систем — одна из них,
/// другой домен — другая.
pub trait WorldModel {
    /// Стабильная идентичность, записываемая в пакет. Воспроизведение под другой моделью отвергается.
    fn identity(&self) -> WorldModelId;

    /// Единственное место, где домен интерпретирует поведение гостя.
    fn handle(&mut self, stop: &Stop, ctx: &mut WorldCtx<'_>) -> Result<Effects, WorldError>;

    /// Сбои, которые эта модель умеет вносить, и моменты, которые она считает опасными.
    fn fault_catalog(&self) -> &FaultCatalog;

    /// Взведённые моделью таймеры в тиках. Ядро сливает их со своей очередью.
    fn next_deadline(&self) -> Option<Tick>;

    /// Срабатывает всё, что подошло к показанию мировых часов. Пробуждения и операции над
    /// узлами возвращаются данными; выполняет их ядро.
    fn on_deadline(&mut self, ctx: &mut WorldCtx<'_>) -> Result<DueEffects, WorldError>;
}
```

**Время движется по одному правилу ядра.** В начале каждой итерации планирования ядро через
`on_deadline` срабатывает всё, что мир взвёл на текущий тик или раньше. Когда планировать некого —
все живые заблокированы или их узлы заморожены, — но таймер взведён, ядро двигает мировые часы прямо
к этому сроку и срабатывает его; и только когда внутри бюджета тиков не взведено ничего, прогон
объявляется взаимно заблокированным, потому что срок, до которого бюджет не даёт дожить, для прогона
не существует. Очередь живёт в мире, потому что срабатывание записи требует знания мира — содержимого
пакета, матрицы разделений на момент доставки, буфера пробуждаемой задачи, — а ядро знает лишь, что
что-то подошло на тике T. Записи упорядочены по `(тик, узел, seq)` и никогда по порядку вставки
(§8.1).

**Следствие для формата.** Пакет записывает `WorldModelId`, и `bohr replay` отвергает пакет,
произведённый другой моделью, вместо того чтобы воспроизвести его в бессмыслицу
([`API.md`](./API.md) §4.2). Без этого первый же междоменный пакет молча дал бы правдоподобный
неверный прогон — режим отказа §5.9 с новой причиной.

Шов стоит одной косвенности на горячем пути, в том же месте и того же размера, что и у §5.2, и
`WorldCtx`, который отдаёт часы, курсор ленты и приёмник трассы, не отдавая владения ни одним из них.

### 5.17. Способ судить о прогоне — тоже порт

`always`/`sometimes` из SDK и встроенные проверки на падение и зависание отвечают на вопрос «повёл ли
себя *этот* прогон неправильно». Это один вид вердикта.

Второй вид не требует ни знания домена, ни разметки вовсе: прогнать одну ленту через две или больше
реализации одной спецификации и проверить, что они согласны. Независимые реализации, обязанные давать
одинаковый результат, — стеки протоколов, движки запросов, виртуальные машины, клиенты консенсуса —
дают оракул бесплатно. Расхождение — по построению дефект в одной из них, и, чтобы сообщить, что они
разошлись, не нужно знать, чьё поведение было верным.

```rust
/// Решает, считается ли прогон — или набор прогонов — находкой.
pub trait Oracle {
    fn identity(&self) -> OracleId;

    /// Судит один прогон по его трассе и записям SDK.
    fn judge(&mut self, run: &RunOutcome) -> Verdict;

    /// Судит набор прогонов друг против друга. Здесь живёт дифференциальное тестирование:
    /// N реализаций, одна лента, сравнение. Возвращает Verdict::Agree при совпадении.
    fn judge_group(&mut self, runs: &[RunOutcome]) -> Verdict { Verdict::Skipped }
}
```

Такой вердикт нельзя выразить утверждением внутри одного гостя, поэтому у него собственный шов. С
групповым оракулом «прогон» — это *набор* исполнений, ведомых одной лентой, и это несут корпус,
редуктор и пакет (§5.20). Любой оракул, составляющий другие, составляет весь интерфейс: панель,
ответившая на `judge` и оставившая `judge_group` умолчанию, тихо перестала бы сравнивать.

#### 5.17.1. Что портом не является

Три дальнейших шва предвидимы, и ни одного из них нет по одной причине: они меняют только внутреннюю
структуру и никогда — формат на диске. Трейт, затрагивающий пакет, обязан появиться до того, как
пакеты станут важны; трейт, затрагивающий только код, может ждать появления второй реализации.

| Кандидат | Почему не трейт |
|---|---|
| `CoverageSource` | три уровня — внутренний enum (§5.10) без влияния на формат |
| `Mutator` | байтовые операторы — одна реализация; структурный мутатор по журналу был бы второй |
| `FaultTargeting` | функция каталога сбоев, а его §5.16 уже делает подключаемым |

### 5.18. Передача прогона отладчику — осмотр, а не продолжение

`bohr replay --break-at` останавливает воспроизведённый прогон на названном событии и отпускает
гостей, чтобы к ним подключился обычный отладчик. Отладчик получает труп, который можно читать:
память, регистры, стек, все потоки. Чего он не может — продолжить.

Об этом заботятся три механизма, переживающие отсоединение. Действие фильтра seccomp по умолчанию —
`Trace(0)`, а отладчик никогда не ставит `PTRACE_O_TRACESECCOMP`, поэтому системный вызов, который
гость делает под gdb, останавливается фильтром, которого никто не слушает, и возвращает `ENOSYS`.
`PR_SET_TSC` выставлен на отказ, поэтому чтение часов поднимает `SIGSEGV`. А детерминизм прогона — это
супервизор, отвечающий на эти вызовы с ленты: продолжившему гостю отвечал бы хост, а именно это вся
конструкция и существует, чтобы предотвратить.

**Ограничения печатаются вместе со строками подключения, каждый раз.** Сделать гостя продолжаемым
означало бы gdb-стаб, отвечающий с ленты, — второй путь перехвата с тем же бременем корректности, что
и первый. Передача, которая напечатала бы строку подключения и промолчала, заработала бы баг-репорт от
первого же человека, набравшего `continue`. `DebuggerTarget` несёт ограничения рядом с командой, а
заполняет их бэкенд, отпустивший гостя.

`PTRACE_O_EXITKILL` снимается перед отсоединением, иначе ядро убило бы гостя при выходе супервизора;
завершение гостя поэтому — обязанность сессии, и `Drop` убивает группу, когда сессия заканчивается.
`--gdb` — это `--break-at 0`, а не второй путь, потому что два способа заморозить прогон — это два
способа заморозить его по-разному.

### 5.19. Третий слой решает, четвёртый выполняет

Исследователь и редуктор не исполняют ничего. Это конечные автоматы: у них спрашивают, что пробовать
дальше, им отдают, что получилось, а гостя запускает `bohr-cli` — крейт, владеющий связыванием.
Трейта `Runner` нет, и ядро его не экспортирует.

**Трейт, используемый только над ядром, — не порт.** `WorldModel`, `Oracle`, `EventSink` и
`SchedulePolicy` объявлены в `bohr-kernel`, потому что их потребляет `run()` (§5.16, §5.17). Трейт,
который ядро никогда не вызывает, — это общий словарь, которому дали неправильный дом.

**Форма конечного автомата — то, что делает центральное утверждение доказуемым, а не проверяемым
глазами.** Кампания — чистая функция своего мастер-сида *потому что* исследователь не может ничего
исполнить: `-j 1` и `-j 8` доказуемо согласуются за миллисекунды против скриптованного бэкенда.
Крейту, держащему `&mut dyn Runner`, можно передать реализацию, читающую часы, и гарантия стала бы
вопросом к ревьюеру вместо свойства структуры.

Это же и форма, которая масштабируется. Когда решающий — конечный автомат, выполняющее его решения
может быть одним процессом, восемью или флотом, и автомат об этом не знает. Решающий, который *вызывал
бы* runner, потребовал бы спрятать за трейтом сеть и заблокировал бы на ней адаптивный цикл. Тот же
довод делает параллельную редукцию аддитивной — `next()` расширяется до «предложить несколько», — а не
перестройкой.

Два места поэтому говорят, как выполнить один сценарий и собрать его артефакты. Ответ на это
дублирование — одна конкретная функция в крейте, владеющем связыванием, а не абстрактный порт слоем
выше.

### 5.20. Одна лента — один источник враждебности, а не одно расписание

`judge_group` сравнивает реализации одной спецификации, ведомые одной лентой. Обосновывает это не
лента.

**Реализации не получают равных условий.** Они делают разные системные вызовы в разном порядке,
поэтому каждая выборка, чья *позиция* зависит от поведения гостя, ложится для каждой из них в другое
место. Общими действительно являются сид и весь байтовый поток; каждая выборка, сделанная до первой
инструкции гостя, то есть смещения часов по узлам, выбираемые в порядке узлов и зависящие только от их
числа; каждый запланированный сбой на фиксированном тике, до которого доходят оба исполнения; и
конфигурация. Общими не могут быть приоритеты планировщика, решения сети по каждому пакету и всё, что
выбирается после того, как гости начали расходиться.

Одна лента даёт им один источник враждебности — одну погоду, а не один день.

**Значение, по которому их сравнивают, поэтому обязано быть таким, равенства которого спецификация
требует при любом допустимом расписании.** Корень состояния после N блоков — такое значение. Дайджест
событий — нет; порядок в логе — нет; всё чувствительное к таймингу — нет. Сравнение любого из них
сообщало бы о расхождении почти на каждом сиде, а режим, кричащий «волки» на каждом сиде, хуже, чем
отсутствие режима.

Отсюда два следствия, и оба не задокументированы, а обеспечены:

- **Выбираемые сбои запрещены рядом со сравнением.** `maybe_kill` выбирает на каждом системном
  вызове — намеренно, чтобы потребление байтов не зависело от состояния диска, — а две реализации
  делают разное число системных вызовов, поэтому выбираемое расписание не может совпасть ни при какой
  конструкции. Запланированные сбои на фиксированных тиках — могут, и совпадают.
- **Сравнение, которого не было, — не согласие.** Проекция, которую одна из реализаций не произвела,
  оставляет вопрос без ответа, а вердикт `Skipped`, свёрнутый в чистый прогон, позволил бы кампании из
  миллиона дифференциальных прогонов отчитаться миллионом чистых, не проверив ничего. Выход
  ненулевой, под `BOHR-5004`.

**Чем дифференциальный прогон не является.** Разнородные кластеры — одна реализация на части узлов и
другая на остальных — вне модели, как и проекция, вычитанная из запроса в виртуальной сети, что есть
разбор протокола. Дифференциальный прогон — это N однородных кластеров, а не один смешанный.

## 6. Модель конкурентности

### 6.1 Внутри супервизора: один поток принятия решений

Цикл прогона ядра однопоточен по построению. Он владеет курсором ленты, часами, планировщиком и
миром, и он единственный, кто их изменяет.

```
loop {
    let stop      = backend.next_stop()?;            // остановлена ровно одна задача
    let effects   = world.handle(stop, &mut cursor)?; // чисто: (состояние, стоп, выборки) -> эффекты
    trace.record(&effects);
    let next      = scheduler.pick(&runnable, &mut cursor);
    backend.resume(next, effects.resume_action)?;
}
```

Никакого `Arc<Mutex<World>>` здесь нет намеренно. Конкурентность в супервизоре внесла бы источник
недетерминизма в компонент, чья единственная цель — их устранение, а профиль этого не оправдывает:
цикл упирается в переключения контекста в гостя, а не в наши вычисления.

**Что имеет право быть конкурентным:** работа, не влияющая на решения — сжатие и запись следа
(ограниченный канал к одному потоку-писателю), рендер отчёта и запуск кампании.

### 6.2 Между прогонами: параллелизм кампании

`bohr explore -j N` гоняет N **независимых** миров в N процессах, у каждого свой сид, своя лента и
свой супервизор. Общего у них ровно две вещи, обе только на дозапись и обе устойчивые к падению:
каталог корпуса и каталог находок.

Изоляция процессами, а не потоками, потому что отказ бэкенда — неожиданное состояние ptrace, гость,
заклинивший нашу бухгалтерию ptrace, — обязан убить одного воркера, а не кампанию. Супервизор — это
системный компонент, разговаривающий с враждебным гостем; предполагать, что он никогда не умрёт, —
не инженерия.

**Инвариант детерминизма при параллелизме:** находка, полученная воркером 7 из 16, обязана
воспроизводиться идентично на `-j 1`. Идентичность воркера, их число и планирование между ними
никогда не имеют права попасть в выборку. Обеспечивается тестом, который гоняет одну кампанию на
`-j 1` и `-j 8` с фиксированным мастер-сидом и сравнивает множества отпечатков находок.

**Как это достигается, а не только декларируется: поколения.** Поиск по покрытию — это петля
обратной связи, поэтому то, что исследуется дальше, зависит от того, что вернулось, — а на
нескольких воркерах то, что вернулось *первым*, есть факт о машине. Поэтому кампания планирует
работу поколениями из корпуса, каким он был к концу предыдущего, и сворачивает результаты поколения
**в порядке планирования**, а не прихода. Каждая свёртка тогда — чистая функция от отсортированного
списка. Ни число воркеров, ни их скорость не дотягиваются до решения, потому что не дотягиваются до
списка работ.

Размер поколения **фиксирован** по той же причине. Задать его через `-j` значило бы вернуть машину в
форму поиска, и один воркер с восемью исследовали бы разное из одного мастер-сида. Воркеры делят
поколение, а не задают его размер.

Цена в том, что поколение кончается вместе с самым медленным своим элементом. Она платится
увеличением поколения в несколько раз относительно числа воркеров, так что отстающий стоит доли
рабочего времени воркера, а не всего; и платится сознательно: поиск, который на несколько процентов
медленнее, стоит того, чтобы его находки мог воспроизвести кто угодно.

### 6.3 Внутри гостя: полный порядок

Гость волен создавать сколько угодно потоков и процессов. Планировщик допускает к исполнению ровно
одного за раз (§5.4). Точки переключения:

вход и выход из системного вызова · вход и выход из примитива синхронизации (`futex` и пути
libpthread, которые до него доходят) · блокирующая операция · `sched_yield`, то есть просьба самого
гостя · явный `fault_point` из SDK.

Один режим на любом хосте (§14.3). Прогон переключается там, где гость входит в ядро, и больше
нигде, поэтому две инструкции, которые гоняются без системного вызова между ними, остаются в том
порядке, в каком их выполнил процессор, — и потому поиск имеет опору на программах, которые между
конфликтующими шагами уступают процессор, пишут в журнал или опрашивают.

Набор точек переключения — это **параметр размена силы поиска на скорость**, и он записывается в
пакет: прогон, использовавший меньше точек переключения, несравним с прогоном, использовавшим больше,
и отчёт говорит, какой был использован.

### 6.4 Политики планирования

`SchedulePolicy` — трейт с одним горячим методом: `pick(runnable, &mut cursor) -> TaskId`.

| Политика | Поведение | Когда |
|---|---|---|
| `random` | равномерно по готовым задачам | базовая линия и запасной вариант, когда ничего лучше не применимо |
| `pct` | PCT (ASPLOS 2010): `d−1` случайных точек смены приоритета, в остальном приоритеты фиксированы. Для `n` задач и `k` шагов баг глубины `d` находится с вероятностью не меньше `1/(n·k^(d−1))` за прогон | по умолчанию для исследования; у большинства реальных багов глубина 1–3 |
| `replay` | решения выводятся из записанной ленты | `bohr replay` и каждый шаг сжатия |
| `adversarial` | смещает переключения к подозрительным местам (около блокировок, около сетевых операций, сразу после записи) | после того, как исследователь локализовал подозрительную область |

PCT стоит по умолчанию вместо `random`, потому что несёт вероятностную гарантию, которой у `random`
нет. Гарантия проверяется против границы из статьи — точка смены попадает в любое место прогона
примерно с равной вероятностью, — а не против другой реализации: второй реализации пришлось бы
доверять, а границе не приходится. AWS Shuttle остаётся эталоном для чтения, когда поведение
вызывает вопросы.

## 7. Пути данных

Полные трассы с бюджетами. Числа целевые, и каждое из них измеряется, а не заявляется
([`TESTING.md`](./TESTING.md) §11).

### 7.1 Системный вызов гостя, от инструкции до записанного события

```
 1. Гость выполняет  clock_gettime(CLOCK_MONOTONIC, &ts)
        │  VDSO нет: AT_SYSINFO_EHDR обнулён при exec, значит это настоящий системный вызов
 2. Ядро вычисляет фильтр seccomp-BPF → SECCOMP_RET_TRACE
        ▼  bohr-backend-ptrace                бюджет: ≤ 12 мкс на трассируемый вызов
 3. Супервизор просыпается на остановке, читает регистры, строит Stop::SyscallEntry { nr, args }
        ▼  bohr-kernel
 4. Диспетчеризация по номеру вызова на обработчик
 5. Обработчик спрашивает мир: «какое время на этом узле?» → часы узла + уход
 6. Обработчик пишет timespec в память гостя через backend.write_mem
 7. Выпускает Event::Syscall { nr, args, ret, tick } в след
 8. Продвигает часы на тактовую стоимость вызова
        ▼  bohr-kernel::scheduler             бюджет: ≤ 1 мкс
 9. Выбирает следующую задачу: policy.pick(runnable, &mut cursor)  ← выборка из ленты
10. Журналирует выборку: (смещение, длина, площадка = SchedPick, выбранная задача)
        ▼  bohr-backend-ptrace
11. Resume::SkipSyscall { ret: 0 } — вызов никогда не доходит до ядра хоста
12. Гость продолжает, считая, что прочитал часы
```

Шаги 5–7 — чистые функции от `(состояние мира, выборки)`, что и делает их тестируемыми на уровне
`bohr-world` вообще без гостя (§5.11).

### 7.2 Сетевой пакет, от `sendto` до доставки

```
 1. Узел A: sendto(fd, buf, …)               → Event::PacketSent
 2. Виртуальная сеть: находит связь A→B
 3. Выборка: доставлен / потерян / продублирован                  ← лента
 4. Выборка: задержка из настроенного для связи распределения     ← лента
 5. Проверка матрицы разрывов, включая односторонние
 6. Постановка на такт = сейчас + задержка в очередь доставки (двоичная куча по такту, затем по
    детерминированному разрешению ничьих, никогда по порядку вставки в хеш-таблицу)
 …
 7. Часы мира доходят до такта доставки              → Event::PacketDelivered
 8. Задача узла B, заблокированная в recvfrom, становится готовой
 9. Планировщик может выбрать её сейчас, а может и нет           ← ещё одна выборка
10. Данные пишутся в память гостя B; recvfrom возвращает
```

Разрешение ничьих на шаге 6 названо отдельно, потому что это классическое место, где умирает
детерминизм: два пакета, назначенных на один такт, обязаны иметь полный порядок, не зависящий от
адресов аллокатора и от порядка обхода хеш-таблицы.

### 7.3 Кампания, от сида до минимального повтора

```
 1. bohr explore --target ./app -j 8 --time 30m
 2. Воркер i берёт ленту из корпуса (или seed_i при холодном старте)
 3. Мутирует: перевороты байт, склейки, havoc — операторы в стиле AFL++ над префиксом
 4. Прогоняет (путь 7.1 × миллионы)
 5. Собирает: битовую карту покрытия, записи SDK, статус выхода, свойства супервизора
 6. Покрытие выросло?        → сохранить ленту в корпус
    Свойство нарушено?       → записать finding-<digest>.bohr, продолжить
 7. По окончании кампании: для каждой различной находки
 8.   bohr reduce: дельта-отладка над лентой и списком событий
 9.     каждый кандидат проверяется полным прогоном: то же нарушение ⇒ сокращение остаётся
10.   сходимость → минимальная лента
11. bohr report: временная шкала, выжившие события, значимые выборки, один HTML-файл
```

Шаг 9 — дорогая часть и причина, по которой сжатие является отдельной командой со своим бюджетом:
сжатие с 40 000 событий до менее чем 20 (цель T5) стоит порядка нескольких сотен прогонов, а это
минутная операция, которую нельзя прятать внутри `explore`.

### 7.4 Путь записи SDK

```
 1. Гость вызывает  bohr::always(invariant_holds, "log is monotonic")
 2. SDK проверяет BOHR_SDK_OUTPUT (или ANTITHESIS_SDK_LOCAL_OUTPUT); не задано → возврат, нулевая цена
 3. Сериализует одну запись JSON, одна строка, пишет в дескриптор
 4. Запись — это системный вызов → мы уже стоим на нём (путь 7.1)
 5. Супервизор разбирает строку, сверяет со схемой, сворачивает в состояние свойств
 6. Event::Assertion { name, kind, hit, condition } попадает в след
 7. always нарушен → прогон становится находкой, останов сейчас
    sometimes → записано; вычисляется только в конце кампании
```

Шаг 4 — то место, где расход не возникает: SDK не нужен собственный транспорт. Он пишет в файловый
дескриптор, а записи и так перехватываются, поэтому в SDK вообще нет кода IPC, специфичного для
Bohr. Именно это оставляет пять языковых SDK небольшими.

## 8. Правила построения кода — Rust

Правила, а не пожелания. Нарушение — блокирующее замечание на ревью; часть проверяется в CI
механически (правило 14).

**1. Инкапсуляция по умолчанию.** Поля структур приватные. Публичны — конструкторы, которые
**валидируют**, и геттеры. Публичное поле означает «инварианта здесь нет»; там, где инвариант есть
(такт монотонен, вероятность в `[0,1]`, смещение ленты внутри префикса), нарушить его снаружи должно
быть невозможно. Исключение — `bohr-types` и `bohr-sdk-proto`, которые по природе DTO: там поля
публичны, а валидация происходит на границе десериализации, а не «где-нибудь потом».

**2. Инварианты — в типах, а не в комментариях.** Newtype на каждый идентификатор: `NodeId`,
`TaskId`, `EventId`, `Fd`, `TapeOffset`, `Tick`. Два параметра `u64`, которые можно перепутать
местами, рано или поздно перепутают, а в этом коде перепутанные `TaskId`/`NodeId` дают неправильный,
но правдоподобный след, что хуже падения. Единицы — в имени поля (`delay_ticks`, `budget_branches`,
`size_bytes`), никогда просто `delay`/`budget`. Там, где ноль недопустим, — `NonZeroU64`.

**3. Композиция, а не эмуляция наследования.** Общее поведение выносится в тип, который
**встраивается** (`struct PctPolicy { rng_sites: Vec<TapeOffset>, … }`), а не в дефолтные методы
трейта, которые каждый реализующий переопределит по-своему.

**4. Трейты на границах, дженерики внутри.** `Box<dyn DeterminismBackend>` уместен: бэкенд
выбирается в рантайме из конфигурации, а виртуальный вызов происходит раз на остановку гостя, где он
шум на фоне переключения контекста. `Box<dyn Fn>` внутри цикла доставки пакетов неуместен. Правило:
динамическая диспетчеризация там, где реализация выбирается в рантайме; мономорфизация во всех
остальных местах.

**5. Никаких кортежей на границах.** Любой тип, пересекающий границу модуля или крейта, — именованный.
`(u64, u64, bool)` в сигнатуре — гарантированная будущая путаница.

**6. Fail fast на границе, деградация внутри.** Невалидный конфиг, битый пакет, обрезанный заголовок
ленты, запись SDK не по схеме — `Result::Err` с внятным сообщением в момент разбора. Никаких
`unwrap_or_default()`, превращающих ошибку в тихий ноль. Но: одна битая строка SDK убивает *эту
запись* (со счётчиком и сэмплом в лог), а не прогон; неподдержанный системный вызов убивает *прогон*
(§5.7), а не кампанию.

**7. Один источник истины для производных величин.** Если тактовая стоимость, задержка или
отображение выборки в значение считаются в двух местах, они разойдутся, а разойдясь, проявятся как
«воспроизведение не воспроизводит» — самый тяжёлый симптом, который мы можем себе устроить. Одна
`#[inline] fn`, протестированная отдельно.

**8. Детерминизм там, где есть стохастика — см. §5.1.** Каждый стохастический выбор берёт явный
`&mut TapeCursor`. Контракт: одинаковый вход плюс одинаковая лента ⇒ побитово одинаковый выход.
Проверяется эталонными тестами над отпечатком следа.

**9. Время через часы, никогда с хоста.** Ни одного `Instant::now()` или `SystemTime::now()` в
`bohr-kernel`, `bohr-world`, `bohr-explorer`, `bohr-reducer`. Настенное время существует ровно в двух
местах, оба исключены из отпечатка: измерение скорости и бюджет кампании.

**10. Упорядоченные коллекции на путях решений.** Порядок обхода `HashMap`/`HashSet` нестабилен между
прогонами. Везде, где порядок обхода может повлиять на решение или на след, тип — это `BTreeMap`,
`BTreeSet` или `IndexMap`. `HashMap` допустим только для чистого поиска без обхода, и вопрос на ревью
всегда один: «а это кто-нибудь обходит?».

**11. `unsafe` только в `bohr-backend-ptrace`, и там с `// SAFETY:` — см. §5.12.**

**12. Ошибки типизованы по крейтам.** `thiserror` в библиотеках, `anyhow` допустим только на самом
верху `bohr-cli`. Каждая ошибка, видимая пользователю, несёт стабильный машиночитаемый код из каталога
([`API.md`](./API.md) §8), что произошло и что с этим делать.

**13. Naming.** Регистр по конвенции Rust. Модули — существительные (`tape`, `scheduler`, `world`),
никогда `utils`/`helpers`/`common`: такие модули накапливают несвязанный код. Функции, которые могут
отказать, названы так, чтобы это было видно (`try_advance`, а не `advance`, если возвращает
`Option`).

**14. Правила, проверяемые машиной.** В CI (`make lint`), а не глазами на ревью:
- `cargo clippy --workspace --all-features -- -D warnings`, `cargo fmt --check`, `cargo deny check`,
  `typos`
- `ptrace|seccomp|waitpid|libc::` отсутствуют вне `bohr-backend-ptrace` (§5.2)
- `unsafe` отсутствует вне `bohr-backend-ptrace` (§5.12)
- `Instant::now|SystemTime::now|thread_rng|rand::random` отсутствуют в sans-io крейтах (§5.1, правило 9)
- `HashMap|HashSet` отсутствуют в модулях решений `bohr-kernel`/`bohr-world` (правило 10)
- только эти два правила пропускают `chaos.rs` — там крейт держит намеренные дефекты, которые стенд
  мутаций включает по одному ([`TESTING.md`](./TESTING.md) §7.4); все остальные правила, включая
  `unsafe`, действуют на них без изменений
- ни один крейт-реализация бэкенда не встречается в дереве зависимостей `bohr-kernel` (§5.2)
- ни одна реализация модели мира или оракула не встречается в дереве зависимостей `bohr-kernel` (§5.16, §5.17)
- набор трассируемых фильтром seccomp вызовов равен набору ключей таблицы обработчиков (§5.6)
- версия формата `.bohr` в коде равна описанной в `API.md` §4
- в коде нет проектной меты: названий этапов, ссылок на дорожную карту, «пока что», «добавим позже» (§8.1)

**15. Публичный API документируется на месте.** `#![warn(missing_docs)]` в `bohr-types`,
`bohr-backend`, `bohr-tape`, `bohr-sdk-proto` и каждом крейте SDK. Это крейты, которые читает
посторонний, и первое впечатление формируется в IDE, а не на сайте.

**16. Комментарии — на английском, по делу и по блокам.** Подробно в §8.1: это правило нарушается
чаще остальных и заслуживает отдельного раздела.

### 8.1 Комментарии

**Язык — только английский. Весь код, все комментарии, все doc-комментарии, все сообщения об ошибках
в коде, все имена — английские. Без исключений.**

Причина не в моде. `bohr_sdk.h` уходит стороннему разработчику; doc-комментарии `bohr-types`
публикуются на docs.rs; отчёт прикладывается к задаче, заведённой мейнтейнеру в другой стране; наши
файлы однажды откроет контрибьютор. Неанглийский комментарий в публичном инструменте — мгновенный
сигнал «это не для посторонних», и он не отменяется никаким README.

Разделение простое и жёсткое:

| Что | Язык |
|---|---|
| Код, комментарии, doc-комментарии, имена, тексты ошибок, логи | **английский** |
| `docs/*.md` | **английский** (каноническая версия) |
| `docs/ru/*.md` | русский, идентичное зеркало |
| Коммиты, описания PR, задачи, обсуждения | английский |
| Gherkin-файлы `.feature` и определения шагов | **английский** — их аудитория это каждый пользователь инструмента ([`TESTING.md`](./TESTING.md) §5) |

Сценарии описывают *контракт продукта* («прогон с тем же сидом даёт тот же отпечаток») и попадают в
цитаты в документации и задачах, поэтому они на английском, а не на языке команды.

**Комментариев ровно столько, чтобы код был понятен. Не больше.**

Комментарий на каждой строке — не «тщательно», а вредно: он удваивает объём для чтения, при первой же
правке расходится с кодом и после этого врёт. Врущий комментарий хуже отсутствующего, потому что ему
верят.

Правило плотности: **комментарий объясняет блок, алгоритм или контракт — не строку.**

Комментируем **зачем**, а не **что**. «Что» уже сказано кодом; если непонятно «что», проблема в
именах и структуре, и чинится она кодом, а не прозой.

**Регистр: повествовательный, а не убеждающий.** Назови ограничение и его следствие — и остановись.
Никакой риторики, никаких историй из окопов, никакого спора с воображаемым рецензентом. Там, где
поведение задано спецификацией, процитируй её и дай ссылку, а не пересказывай. Рассуждение, приведшее
к решению, живёт в этом документе, где его можно обсудить и пересмотреть; исходники несут само
решение и одну фразу, которой читателю хватит, чтобы его не сломать.

```rust
// Правильно — ограничение, следствие, точка.
// Reads spanning the prefix boundary are stitched here rather than by callers: an off-by-one
// in the split changes how the tape decodes at exactly one length.

// Неправильно — тот же факт, но при параде.
// Reads that straddle the prefix boundary are stitched here rather than by callers, because a
// caller that got the split wrong would produce a tape that decodes differently at one specific
// length — the kind of bug that shows up once in ten thousand runs and costs a week.
```

У каждого публичного поля есть `///`, обычно в одну строку. Разворачивать только там, где иначе
проектное ограничение останется невидимым: граница, существующая ради обратного давления, порядок,
существующий ради детерминизма.

**Где комментарий обязателен:**

- `///` на каждом `pub`-элементе в крейтах из правила 15 — это контракт, а не украшение;
- нетривиальный алгоритм: одна-две строки о том, какой подход и почему именно он (назначение
  приоритетов PCT, стратегия деления в дельта-отладке, отображение выборки в значение);
- инвариант, не выражаемый системой типов («caller must hold the task stopped»);
- `// SAFETY:` на каждом `unsafe` с описанием инварианта, который обязана соблюсти вызывающая сторона;
- обход странности ядра или libc — **со ссылкой** на man-страницу, коммит или задачу. Без ссылки через
  полгода это выглядит как ошибка, и её «чинят»;
- сознательно неочевидное решение: почему **не** сделано очевидным способом;
- всё, что влияет на детерминизм. Строка, выглядящая избыточной, но существующая ради стабильности
  порядка, обязана об этом сказать, иначе её удалят в PR по уборке, и мы потратим на это неделю.

**Где комментарий запрещён:**

- пересказ кода (`// increment counter` над `counter += 1`);
- закомментированный код — для этого есть git;
- `TODO` без владельца и ссылки на задачу: безадресный TODO живёт вечно;
- декоративные разделители из символов на всю ширину экрана;
- doc-комментарий на очевидном геттере (`/// Returns the id.` — шум, а не документация);
- дублирование того, что уже написано в `docs/`. Вместо копии — ссылка
  (`// See docs/API.md §2.4 for the draw ABI`), потому что копия разойдётся с оригиналом;
- **любая проектная мета** — названия этапов, ссылки на дорожную карту, сроки, «пока что»,
  «временно», «добавим позже». Комментарий описывает код таким, какой он есть. Как только он
  начинает описывать план, он устаревает и начинает врать, а тот, кому нужен план, ищет его не в
  исходниках. Если ограничение реально, описывай само ограничение и его следствие, но никогда не
  срок, к которому оно снимется.

Правильно:

```rust
// Tie-break by (tick, node, seq) and never by insertion order: two packets scheduled for the
// same tick must have a total order that does not depend on allocator addresses.
// See docs/ARCHITECTURE.md §7.2.
struct DeliveryQueue(BinaryHeap<Reverse<(Tick, NodeId, u64)>>);

impl TapeCursor {
    /// Draws a value in `0..n` and records the draw in the journal.
    ///
    /// Rejection sampling rather than modulo: modulo biases low values, and a biased scheduler
    /// draw silently reduces the bug classes PCT can reach. The bias is invisible in tests and
    /// only shows up as "we never find depth-3 bugs".
    pub fn draw_range(&mut self, n: u64, site: DrawSite) -> u64 { /* ... */ }
}

// SAFETY: `addr` is a guest address validated against the task's mappings above, and `buf` is
// owned by us for the whole call. process_vm_readv does not write outside `buf`.
unsafe { libc::process_vm_readv(pid, &local, 1, &remote, 1, 0) };
```

Неправильно:

```rust
// Структура очереди доставки                ← не английский
struct DeliveryQueue {
    heap: BinaryHeap<Item>,  // куча          ← пересказ кода
    len: usize,              // длина         ← пересказ кода
}
// TODO: подумать                             ← без владельца, без ссылки, вечный
```

### 8.2 Авторство в git

**Все действия с репозиторием выполняются от лица разработчика. Единственный автор — человек.**

- В сообщениях коммитов **запрещён** трейлер `Co-Authored-By` с любым ассистентом.
- В описаниях PR **запрещены** футеры вида «Generated with …».
- Упоминания инструментов разработки не попадают в git-историю, теги и релизные заметки ни в каком
  виде.

Причина простая: авторство в истории репозитория — решение владельца репозитория, и история проекта
читается как работа команды. Инструмент, которым набран текст, к авторству отношения не имеет и в
`git log` ему делать нечего.

Правило продублировано в `AGENTS.md` и `CLAUDE.md` в корне репозитория — там, где его прочитает
автоматика.

### 8.3 Коммиты

Маленькие, и сообщение — про самое важное.

- **Conventional Commits** с необязательной областью: `<type>(<scope>): <short description>`.
  Типы: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `chore`. Область — крейт или зона
  (`tape`, `kernel`, `ptrace`, `explorer`, `cli`).
- Заголовок в повелительном наклонении, строчными, без точки в конце, ≤ 72 символов.
- Тело необязательно и отвечает на **почему**, одним-тремя предложениями. Оно никогда не перечисляет
  изменённые файлы — для этого есть дифф. Никаких «всеобъемлющий», «надёжный», «улучшить»,
  «задействовать».
- Одно логическое изменение на коммит. Промежуточные коммиты схлопываются до ревью.
- Коммит, меняющий поведение, значимое для детерминизма, явно указывает влияние на сохранённые
  пакеты: `BREAKING: invalidates bundles with tape ABI < 2`.

```
fix(kernel): break packet delivery ties by (tick, node, seq)

Insertion order into the delivery heap depended on hash iteration, so two
packets scheduled for the same tick could swap under a different allocation
pattern. Digests diverged roughly once in 4000 runs.
```

## 9. Правила построения кода — SDK и языковые обёртки

SDK — это другой мир с другими правилами, потому что их читатели — разработчики чужих компаний, а их
код живёт внутри чужих сборок.

**S1. В SDK нет логики.** SDK делает три вещи: проверяет, настроен ли канал вывода, сериализует
запись, пишет строку. Ни одного решения о том, выполняется ли свойство, ни одной агрегации, ни одного
повтора. Всё вычисление — в супервизоре. Практический критерий: любой SDK можно выбросить и переписать
за два дня человеку, прочитавшему только [`API.md`](./API.md) §6.

**S2. Нулевая цена при выключении.** Вне Bohr каждый вызов SDK — это проверка одного закешированного
булева и возврат. Ни выделения памяти, ни форматирования, ни ленивой инициализации на горячем пути.
Команда, замерившая замедление от нашего SDK, удаляет наш SDK, и будет права.

**S3. Ноль сторонних зависимостей.** Ни библиотеки JSON, ни фреймворка логирования, ни асинхронного
рантайма. Схема записей достаточно мала, чтобы сериализовать её руками на каждом из пяти языков, а
каждая добавленная зависимость — это конфликт версий в чужой сборке и тикет в поддержку у нас.

**S4. Схема общая, код — нет.** Все пять SDK выдают записи, проходящие одну и ту же JSON Schema, и
набор тестов каждого SDK валидирует свой вывод против этого файла схемы. Мы не разделяем код между
языками; мы разделяем контракт и тест соответствия ([`TESTING.md`](./TESTING.md) §6).

**S5. Совместимость с Antithesis — это тест, а не намерение.** Каталог фикстур хранит записи, снятые с
их SDK. Тест утверждает, что мы разбираем их все и что наш собственный вывод принимается их описанной
схемой. Сдвиг их формата делает этот тест красным.

**S6. Идиоматично по языку, идентично по поведению.** Rust получает `#[track_caller]` и макрос,
захватывающий текст выражения; Python — декоратор и контекстный менеджер; C# — `[Conditional]` и
`CallerMemberName`; Go — обычные функции; C — макросы. Один и тот же вызов на пяти языках порождает
одну и ту же запись.

**S7. Комментарии в SDK — по §8.1.** Doc-комментарии на каждом публичном члене: `///` в Rust,
docstring в Python, `/// <summary>` в C#, doc-комментарии в Go, `/** */` в C. Всё на английском.

## 10. Ошибки, наблюдаемость, конфигурация

**Ошибки.** Один тип ошибки на крейт (`thiserror`); `anyhow` только на самом верху `bohr-cli`.
Каждая ошибка, видимая пользователю, несёт стабильный код `BOHR-####` из каталога в
[`API.md`](./API.md) §8. Коды никогда не переиспользуются под другой смысл — код попадает в лог CI и
в задачу, и его переназначение делает всю историю этих логов неверной.

Три класса ошибок с разной обработкой:

| Класс | Пример | Обработка |
|---|---|---|
| Конфигурация и использование | плохой флаг, отсутствующая мишень, несовпадение версии пакета | падаем до запуска гостя, код выхода 2 |
| Угроза детерминизму | неподдержанный вызов, ненейтрализованный `RDRAND`, недоступный счётчик переходов | прерываем прогон или помечаем `degraded`, никогда не продолжаем молча |
| Находка | нарушено свойство, падение гостя, зависание | **не ошибка**: это успешный прогон, который что-то нашёл, код выхода 1 |

Коды выхода — часть контракта ([`API.md`](./API.md) §7.6), потому что конвейер CI по ним ветвится:
`0` чисто, `1` находка, `2` использование, `3` внутренняя ошибка.

**Логи.** `tracing`, по умолчанию человекочитаемо, `--log-format json` для CI. Обязательные поля
спана там, где применимо: `run_id`, `seed`, `node`, `task`, `tick`. **Никогда не логируется:**
содержимое памяти гостя, его окружение и аргументы командной строки на уровне `info` и выше — сборка
клиента запускается под нами с продакшн-конфигурацией, и его секреты лежат в её окружении. Они
появляются только на `debug` и только за явным флагом `--unsafe-log-guest-env`, имя которого выбрано
неудобным для набора.

**Метрики.** Супервизор — не сервис и Prometheus не поднимает. Он пишет сводку прогона в след и
сводку кампании в JSON:

- выполнено прогонов, прогонов в секунду, инструкций гостя в секунду, коэффициент замедления
- трассируемые системные вызовы против отфильтрованных — прямая мера того, окупается ли §5.6
- покрытие: найдено рёбер, размер корпуса, время с последнего нового ребра
- находки по классам, различные находки после дедупликации по отпечатку
- свойства `sometimes`/`reachable`, всё ещё не удовлетворённые, — «карта непроверенного» из §4.6
- активные флаги деградации (§5.8): число прогонов, которые не были полностью детерминированы

**Конфигурация.** Файл TOML плюс флаги плюс окружение `BOHR_*`, в этом порядке приоритета,
валидируется при старте, fail fast. Итоговая конфигурация после слияния **записывается в пакет**,
потому что «у меня воспроизводится» обычно означает разницу в конфигурации, и мы должны уметь доказать
это одним диффом. `bohr doctor` проверяет хост, конфиг и мишень, ничего не запуская
([`API.md`](./API.md) §7.5).

## 11. Безопасность и данные

| Вопрос | Решение |
|---|---|
| Это песочница безопасности? | **Нет.** README это заявляет. Bohr даёт воспроизводимость, а не изоляцию. Злонамеренный гость может сбежать — надзор через `ptrace` не является границей безопасности. Та же оговорка была у Hermit. Недоверенный код надо запускать в виртуальной машине, с нами или без нас. |
| Данные гостя | Никогда не покидают машину. Пакеты пишутся локально; ничего не выгружается; нет ни телеметрии, ни звонков домой, ни краш-репортера. Для открытого инструмента это безусловно. |
| Пакеты содержат данные гостя | Пакет содержит отпечатки бинарников, аргументы системных вызовов и память, которую гость читал или писал. **Это данные клиента**, и `bohr report --redact` вместе с описанным списком содержимого пакета ([`API.md`](./API.md) §4.6) существуют, чтобы пакет прикладывали к публичной задаче осознанно, а не случайно. |
| Требуемые права | Непривилегированный пользователь с правом `ptrace` на свои процессы и непривилегированными пространствами имён пользователей. Root нам не нужен и никогда не запрашивается. Там, где настройка ядра нас блокирует (`kernel.yama.ptrace_scope`, `perf_event_paranoid`), `bohr doctor` называет настройку и точную команду для её проверки — и мы никогда не меняем настройки хоста сами. |
| Изоляция сети гостя | Фильтр системных вызовов, действие которого по умолчанию — трассировать: всякий сетевой вызов либо доходит до модели, либо отказывается по имени, а в списке разрешённых только вызовы, меняющие собственное адресное пространство гостя, его сигналы или его же exec. Гость под Bohr не может дотянуться до настоящей сети **по построению**, и это же делает симуляцию сети полной. Раньше эту роль играло сетевое пространство имён; оно снято, потому что не охраняло ничего сверх фильтра, а стоило 180 КБ невытесняемой памяти ядра на гостя против 4 КБ на все остальные пространства вместе — и упирало хозяина в потолок по числу кампаний. |
| Нумерация процессов гостя | Пространство имён идентификаторов, внутри которого гость создаётся, а не в которое переносится: поток хранит собственный идентификатор в памяти и ждёт на нём, поэтому одной хостовой нумерации, дошедшей до гостя, достаточно, чтобы прогон разошёлся сам с собой. |
| Файловая система гостя | Пространство имён монтирования со своим корнем. Записи идут на виртуальный диск в супервизоре, а не в файловую систему хоста, если путь не проброшен явно. |
| Переписывание бинарников (§5.8) | Выключено по умолчанию, включается `--patch-rdrand` и работает над **копией**. Мы никогда не изменяем файл, который дал нам пользователь. |
| Цепочка поставок | `cargo deny` в CI на каждый коммит: лицензии, уязвимости, дублирующиеся версии и явный список разрешённых источников. Инструмент детерминизма, притащивший скомпрометированную зависимость, хуже отсутствия инструмента. |

## 12. Дистрибуция

`bohr` — это бинарник. В первый год деплоить нечего.

- **Цели сборки:** `x86_64-unknown-linux-gnu` и `x86_64-unknown-linux-musl`. Сборка на musl
  статическая, и именно на неё ссылается документация, потому что самый частый первый контакт — это
  минимальный CI-контейнер.
- **Воспроизводимые сборки.** Инструмент, обещающий воспроизводимость, сам
  воспроизводим. Зафиксированный тулчейн в `rust-toolchain.toml`, `--locked` везде,
  `SOURCE_DATE_EPOCH` и джоб CI, который собирает дважды на разных раннерах и сравнивает хеши.
- **Распространение:** GitHub Releases с `.tar.gz` на цель и файлом `SHA256SUMS`; установочный скрипт
  `bohrup`; образ контейнера для CI. Никаких пакетных менеджеров в первый год — это сопровождение,
  которого мы себе пока не можем позволить.
- **Публикация SDK:** crates.io, PyPI, NuGet, Go modules. Каждая версия SDK объявляет минимальную
  нужную версию `bohr`; несовпадение — диагностика при старте, а не загадка.
- **Версионирование:** инструмент по SemVer. Два контракта версионируются **независимо** и
  объявляются в каждом пакете: ABI ленты и формат пакета ([`API.md`](./API.md) §9). Обновление
  инструмента не имеет права молча обесценить сохранённую находку — оно либо её воспроизводит, либо
  отказывается с названной разницей версий.
- **Матрица поддерживаемых хостов** и минимальная версия ядра — в [`PLATFORMS.md`](./PLATFORMS.md), и
  они проверяются CI, а не утверждаются прозой.

## 13. Вне области

Чего Bohr не делает и почему каждый пункт — свойство конструкции, а не упущение.

| Не делается | Почему |
|---|---|
| Хосты Windows и macOS | `ptrace`, `seccomp`, `prctl(PR_SET_TSC)` и `arch_prctl(ARCH_SET_CPUID)` есть только в Linux |
| Архитектуры кроме x86-64 | обработка `RDTSC`/`CPUID` и счётчик переходов архитектурно-специфичны |
| Графический интерфейс | отчёт — статический HTML-файл (§5.13); десктоп или веб — отдельный продукт |
| Настоящее многоядерное исполнение | по построению исполняется одна задача за раз (§5.4) |
| `io_uring` | второй, асинхронный путь системных вызовов, подающий работу без вызова на операцию, поэтому гость с кольцом не наблюдается, а не моделируется частично. Отвергается по имени под `BOHR-2004` |
| Прямой доступ к устройствам и DMA | недостижимо выше гипервизора |
| Песочница безопасности | не та постановка задачи, и заявлять это было бы неправдой (§11) |
| Замена обычным тестам | Bohr их дополняет; проект без модульных тестов выиграет мало |
| Инструментирование на уровне языка | переписывание байткода — другой инструмент с другими разменами, и оно ломает свойство «без правок кода» |
| Распределённое планирование кампаний | `-j N` на одной машине — единица параллелизма (§6.2) |
