# Платформы и требования к хосту

Живой документ. Описывает, что именно машина обязана предоставить для запуска Bohr, как должна
выглядеть гостевая программа, какие системные вызовы обрабатываются и какие окружения враждебны.
Всё здесь проверяется `bohr doctor` и CI, а не утверждается прозой.

## 1. Поддерживаемые хосты

| | v1 |
|---|---|
| Операционная система | Linux |
| Архитектура | x86-64 |
| Минимальное ядро | **5.4** |
| Рекомендуемое ядро | 5.15 и новее |
| libc | любая; супервизор поставляется статическим бинарником на musl |
| Права | обычный пользователь. **Root никогда не требуется и никогда не запрашивается.** |

Всё остальное — macOS, Windows, aarch64, 32 бита — вне объёма v1
([`ARCHITECTURE.md`](./ARCHITECTURE.md) §13). Слои выше бэкенда собираются и тестируются на любой ОС
против `bohr-backend-null` ([`TESTING.md`](./TESTING.md) P2), поэтому разработка не только под
Linux, хотя продукт — только под Linux.

**Почему 5.4, а не старше.** Это самое старое ядро, где есть все возможности из §2 с той семантикой,
на которую мы опираемся, и это нижняя граница дистрибутивов, которые реально крутят наши целевые
пользователи. Поддержка более старых ядер означает условные пути перехвата, а условный перехват —
это то, как детерминизм становится зависимым от окружения.

## 2. Требуемые возможности ядра

`bohr doctor` проверяет каждую и печатает точное средство исправления при отказе.

| Возможность | Для чего | Ядро | Отказ |
|---|---|---|---|
| `ptrace` с `PTRACE_SEIZE`, `PTRACE_GET_SYSCALL_INFO` | цикл перехвата | 4.3 / 5.3 | `BOHR-3001` |
| `seccomp` с `SECCOMP_RET_TRACE` и `SECCOMP_FILTER_FLAG_TSYNC` | предфильтр системных вызовов (§5.6) | 3.5 / 3.17 | `BOHR-3003` |
| `arch_prctl(ARCH_SET_CPUID, 0)` | перехват `CPUID` | 4.12 **и** отказ по CPUID, предоставленный процессором | `BOHR-3004`, прогон помечается деградированным |
| `prctl(PR_SET_TSC, PR_TSC_SIGSEGV)` | перехват `RDTSC` | 2.6 | `BOHR-3004` |
| `personality(ADDR_NO_RANDOMIZE)` | отключение ASLR | древнее | `BOHR-3004` |
| пространства имён пользователей без привилегий | изоляция mount, uts, ipc | 3.8 | прогон помечается деградированным |
| пространство имён монтирования | своё распространение монтирований | 3.8 | прогон помечается деградированным |
| `sched_setaffinity` | привязка к одному ядру | древнее | только предупреждение |
| `process_vm_readv` / `process_vm_writev` | быстрый доступ к памяти гостя | 3.2 | откат на `PTRACE_PEEKDATA`, медленнее в ~20 раз, предупреждает |
| `perf_event_open` с аппаратными счётчиками переходов | точное измерение прогресса (§5.5) | 3.4 | `BOHR-2005`, деградация до гранулярности системных вызовов |

### 2.1 Отказ по CPUID — возможность железа, а не версия ядра

`arch_prctl(ARCH_SET_CPUID, 0)` требует `X86_FEATURE_CPUID_FAULT`, который ядро читает из
модельно-специфичного регистра. Должны выполняться три условия сразу, и вызов возвращает `ENODEV`,
если не выполнено любое из них:

| Требование | Подробность |
|---|---|
| процессор это умеет | Intel начиная с Ivy Bridge; AMD начиная с ядра Linux 6.17, где появилась поддержка AMD |
| ядро достаточно новое | 4.12 на Intel, 6.17 на AMD |
| платформа отдаёт регистр | гипервизор, не пробрасывающий его, скрывает возможность даже у способного процессора |

`grep cpuid_fault /proc/cpuinfo` отвечает на все три сразу.

Там, где её нет, гость видит настоящий процессор. Следствие делится надвое:

| | Эффект |
|---|---|
| Та же машина, тот же сид | не затронуто — хост отвечает на `CPUID` одинаково каждый прогон, воспроизводимость сохраняется |
| **Разные машины** | **сломано** — два хоста отвечают по-разному, и пакет между ними не воспроизводится |

Поэтому бэкенд сообщает `traps_cpuid: false`, прогон записывается как `determinism: degraded` с
названной причиной, и межмашинная воспроизводимость для него не заявляется. Ничего не понижается
молча: деградированный прогон никогда не отчитывается как чистый.

Заведомо отсутствует в гостях Hyper-V, к которым относятся WSL2 и любой контейнер поверх него.

### 2.2 Настройки хоста, которые нас блокируют

Это настройки, а не возможности. Мы о них сообщаем и печатаем команду проверки; **настройки хоста мы
никогда не меняем сами.**

| Настройка | Требуется | Симптом при неверном значении |
|---|---|---|
| `kernel.yama.ptrace_scope` | `0` или `1` (1 подходит: мы родитель) | `ptrace` запрещён, `BOHR-3001` |
| `kernel.unprivileged_userns_clone` | `1` там, где она есть (производные Debian) | не создаются пространства имён, `BOHR-3002` |
| `user.max_user_namespaces` | `> 0` | то же |
| `kernel.perf_event_paranoid` | `≤ 2` для счётчиков переходов | `BOHR-2005`, деградированное измерение прогресса |
| `/proc/sys/vm/overcommit_memory` | любое | ни на что не влияет; отмечено, потому что гости иногда от неё зависят |

## 3. Окружения

| Окружение | Статус | Примечания |
|---|:---:|---|
| железо, обычный дистрибутив | **поддержано** | эталонное окружение |
| виртуальная машина (KVM, VMware, Hyper-V) | **поддержано** | счётчики переходов часто недоступны; ожидается деградированное измерение прогресса |
| Docker, профиль по умолчанию | **нужны флаги** | профиль seccomp по умолчанию блокирует `ptrace`. Запускать с `--cap-add=SYS_PTRACE --security-opt seccomp=unconfined` |
| Docker, наш опубликованный образ | **поддержано** | несёт профиль и документирует флаги |
| GitHub Actions `ubuntu-latest` | **поддержано** | проверяется в CI; счётчиков переходов нет, поэтому L4 идёт с гранулярностью системных вызовов |
| поды Kubernetes | **нужна настройка** | право `SYS_PTRACE` плюс ослабленный профиль seccomp; во многих кластерах запрещено и то и другое |
| WSL2 | **частично** | работает для L0–L3; `perf_event_open` и часть конфигураций пространств имён ненадёжны. Не целевая платформа, и `doctor` об этом говорит |
| гости gVisor, Firecracker | **не поддержано** | их реализации системных вызовов отличаются от ядра, под которое мы моделируем |
| вложенность под другим супервизором `ptrace` | **не поддержано** | отклоняется именованной ошибкой |

Строка про Docker важнее, чем кажется: самый частый первый контакт с таким инструментом — это
`docker run` в чьём-то CI, а первый контакт, падающий с «Operation not permitted», — это
пользователь, о котором мы больше никогда не услышим. Опубликованный образ и два флага описаны в
README, а не спрятаны здесь.

## 4. Матрица поддержки гостей

### 4.1 Бинарники

| | Статус |
|---|:---:|
| динамически слинкованный ELF, glibc | поддержан |
| динамически слинкованный ELF, musl | поддержан |
| статически слинкованный ELF | поддержан |
| PIE и не-PIE | поддержаны |
| бинарники с `setuid` | отклоняются — их нельзя трассировать без привилегий, а сделать это означало бы заявление о безопасности, которого мы не делаем |
| интерпретируемые программы (`#!`) | поддержаны; гостем становится интерпретатор |
| JIT-рантаймы (JVM, .NET, V8) | **частично** — работают, но используют `RDRAND`, обильные `mmap`-раскладки и собственные пулы потоков. Ожидается деградированный детерминизм, пока не измерено по каждому рантайму |
| программы с `io_uring` | **поддерживаются через свой запасной путь.** Открытие кольца отвечено `ENOSYS` — это ядро, собранное без этой опции, и путь на такой ответ держит всякая подобная программа; вход в кольцо и его регистрация отвергаются, `BOHR-2004` ([`DETERMINISM.md`](./DETERMINISM.md) §2.8). Прогон идёт не тем путём, каким идёт продакшен, и каждый прогон говорит об этом на своей же ленте. `bohr doctor --target` предупреждает там, где имя встречается в бинарнике; `bohr survey` говорит, вызывается ли оно |
| программы, использующие `ptrace` | отклоняются |
| убийство узла, у которого больше одной задачи | поддержано — воспроизводитель, определявший эту строку, больше не воспроизводится; см. ниже |

**Убийство узла, у которого больше одной задачи, и что стало со стеной.** Несколько потоков одного
узла, читающих один сокет, — обычная форма сервиса, и сокетная половина отвечена: каждый паркуется
по очереди, а доставка освобождает того, кто ждёт дольше всех. Убийство такого узла раньше вешало
прогон — супервизор стоял в своём ожидании, одна гостевая задача уже остановлена и ждала
возобновления, а оставшийся поток убитого узла был зомби, о смерти которого супервизор так и не
узнавал, — и эта строка так и говорила.

**Воспроизводитель, определявший эту строку, больше не воспроизводится.**
`examples/mdbx-hunt/scenario.toml` был назван здесь потому, что замирал с двумя своими таблицами
`[[fault]]` и проходил чисто без них. Теперь он проходит чисто с ними: десять семян, пять задач,
убийство и перезапуск, каждый прогон доходит до конца и отвечает на свои вопросы. Записано в
`benches/baseline.toml` под `[m4_2.multi_task_kill]`.

Чем это измерение является и чем нет. Это один сценарий, поэтому честная формулировка — что ушла та
форма, из которой строка была написана, а не что ушли все. Более узкие были покрыты всегда — одна
задача на узел, убиваемая и перезапускаемая сколько угодно, потоки без убийства и поток, созданный
и присоединённый вокруг любого из них, — а настоящий клиент исполнения, многопоточный по своей
природе, с тех пор был убит несколько сотен раз за кампании и ни разу не завесил прогон.

Ничто здесь не чинилось намеренно, и это та часть, которую стоит записать: работа, закрывшая стену,
была в другом месте, а ограничение, которое никто не перемеряет, переживает дефект, стоявший за
ним. Эта строка перемеряется, когда меняется кампания против многопоточной цели.

**Как собрать гостя, чтобы поиск видел, что внутри.** Всё перечисленное выше работает без
изменений. Пересборки требует только покрытие — просто потому, что ни один бинарник не сообщает о
своих рёбрах сам:

```
clang  -fsanitize-coverage=trace-pc-guard  ... ваш.c sdk/c/bohr-cov-rt.c
gcc    -fsanitize-coverage=trace-pc        ... ваш.c sdk/c/bohr-cov-rt.c
```

Clang помечает каждое ребро переменной-меткой; GCC предлагает только простую форму, и рантайм берёт
ребро из адреса возврата. Оба варианта здесь воспроизводимы, потому что гость и так работает
статически слинкованным и с выключенной рандомизацией адресов: условия, делающие повторимым прогон,
делают повторимой и его карту.

**Рантайм собирается без той инструментации, которую сам реализует.** Собранная с ней функция,
записывающая ребро, записывает рёбра внутри себя, и первое же из них не возвращается.

Гость, собранный без всего этого, всё равно исследуется — расписанием и целеуказанием сбоев,
которым покрытие не нужно, — и сообщается как исследованный без него. Это другое утверждение,
нежели «гость ничего не покрыл», и эти два никогда не сливаются.

### 4.2 Поддержка системных вызовов

Таблица живёт в коде, в `crates/bohr-backend-ptrace/src/linux/syscalls.rs`, и порождает и фильтр
seccomp, и диспетчеризацию обработчиков — они не могут разойтись
([`ARCHITECTURE.md`](./ARCHITECTURE.md) §5.6). Этот раздел описывает классы; текущую таблицу печатает
`bohr doctor --syscalls`.

| Класс | Обработка | Примеры |
|---|---|---|
| **эмулируемые** | до хоста не доходят, отвечает мир | `clock_gettime`, `getrandom`, `read`, `write`, `pread64`, `pwrite64`, `openat`, `ftruncate`, `fsync`, `futex`, `nanosleep`, `getpid`, `gettid`, `uname`, `sendto`, `recvfrom` |
| **виртуализуемые** | транслируются и выполняются над приватным ресурсом хоста | анонимный `mmap`, `mprotect`, `brk` |
| **пропускаемые** | проходят, потому что не могут повлиять на детерминизм | `mprotect`, `munmap`, `mremap`, `brk`, маска сигналов и `clone`, чья новая задача объявляется отдельным событием трассировки |
| **пропускаемые по аргументу** | проходят только в тех формах, что не могут дотянуться до файла | один `mmap`: отображение, ни на что не опирающееся, и собственный канал покрытия этого движка. Всякое другое отображение называет дескриптор, а не страницу, поэтому трассируется и отклоняется |
| **отклоняемые** | `BOHR-2001` или отдельный код | `io_uring_enter`, `io_uring_register`, `ptrace`, `kexec_load`, `bpf` |
| **неизвестные** | `BOHR-2001` с номером вызова и задачей | всё, чего нет в таблице |

**Замок, чьё слово называет владельца** — `FUTEX_LOCK_PI`, `FUTEX_TRYLOCK_PI`, `FUTEX_UNLOCK_PI` —
отвечается, а наследование приоритета, по которому ядро его назвало, не моделируется вовсе:
приоритетов здесь нет, и задача выполняется одна за раз. Моделируется та половина, которую гость
видит: слово держит владельца, второй поток встаёт за ним в очередь, и замок переходит от одного к
другому внутри снятия, а не бросается им на растерзание. Хранилищу, держащему такой мьютекс в
отображаемом файле, нужно ровно это. Операция вне отвеченного набора возвращает `EINVAL` и
называется на ленте времени, потому что собственное сообщение вызывающего о ней не говорит ничего:
падение происходит внутри его библиотеки C, за несколько кадров от всего, что упоминает futex.

**Готовность** — `epoll_create1`, `epoll_ctl`, `epoll_wait`, `epoll_pwait`, `eventfd2` — отвечает
кластерная модель, а не собственный мир узла: набор готовности охватывает и файлы узла, и его
сокеты, а вместе их видит только кластер. Одноузловой прогон без сценария сокетов не имеет и
отклоняет их как прежде. На этом семействе построен всякий асинхронный рантайм; `tokio` 1.53 на
нём работает.

**Сокеты** бывают двух родов, и модель обходится с ними настолько же по-разному, насколько
различны их транспорты. Датаграммы — `sendto`, `recvfrom` — получают четыре выборки и могут
пропасть, удвоиться, обогнать друг друга или опоздать. Потоки — `listen`, `accept`, `accept4`,
`connect`, `getpeername` и `read`/`write` над тем, что они порождают, — не получают ни одной,
потому что транспорт, который они изображают, переспрашивает, пока все четыре не исчезнут.
Единственная напасть, достающая поток, — недостижимость дальнего конца: разрыв придерживает байты
до заживления, а закрытый, полузакрытый или убитый сосед оставляет читателю конец потока. Семантика
нормативна в [`API.md`](./API.md) §5.3 — вместе с тем, что намеренно не моделируется.

**Неизвестный — это жёсткий отказ, никогда не пропуск.** Это §5.7, и именно оно отличает нас от
режима отказа Hermit. Дисциплина объёма, которая делает это выносимым: таблица растёт только тогда,
когда запись нужна реальной мишени, с приоритетом по отчёту «встречено, но не обработано», который
выдаётся заранее, а не по одному вызову за прогон.

Этот отчёт — **`bohr survey -- <программа>`**. Он отвечает `ENOSYS` на каждый вызов, который эта
сборка не моделирует, чтобы добраться до следующего, и печатает весь набор со счётчиком по каждому.
Это не прогон и спутать его с прогоном нельзя: его миры несут собственную личность, поэтому пакет,
заявляющий такой мир, отклоняется до воспроизведения; он ничего не пишет; и он выходит с кодом 4,
если что-то нашёл, — потому что найденное относится к этой сборке, а не к гостю.

Он собирает **стены двух родов** и называет, какого именно, потому что чинятся они по-разному:

| Стена | Что означает | Что нужно |
|---|---|---|
| `nothing models it` | строки в таблице нет; обычный прогон отклоняет вызов по имени | строка и модель за ней |
| `answered ENOSYS` | строка есть, и модель намеренно говорит, что не умеет, — вызывающий уходит на запасной путь, который держит для ядра постарше | модель; строка уже есть |

Второй род собирает только обследование: обычный прогон отвечает молча, потому что запасной путь и
есть смысл ответа вместо отказа. Но со стороны гостя обе стены останавливают его одинаково, и
обследование, называющее лишь первую, позволило бы программе, не сдвинувшейся с места, выглядеть
обследованной начисто.

**Доказательством чего обследование не является** — печатается рядом с каждым отчётом и повторено
здесь, потому что это та часть, которая вводит в заблуждение. Вызов, на который ответили `ENOSYS`,
уводит гостя на запасной путь, по которому он бы не пошёл: программа, которой отказали в
`io_uring_setup`, берёт `epoll` и вообще никогда не выдаёт `io_uring_enter`. А вызов, до которого
прогон не дошёл, — это не вызов, которого программа не может сделать. Набор является нижней
границей дважды, и повышают доверие к нему новые зёрна и более длинные прогоны, а не более
сильное прочтение одного.

### 4.3 Файловая система, на которой гость стартует

Живёт в супервизоре и никогда на хосте: прогон обязан начинаться с одного и того же состояния, а
файл, оставшийся с прошлого прогона, — это состояние. В начале есть корень и каталоги стандарта
иерархии — `/bin`, `/dev`, `/etc`, `/home`, `/lib`, `/opt`, `/proc`, `/root`, `/run`, `/sbin`,
`/srv`, `/sys`, `/tmp`, `/usr`, `/var`, `/var/tmp`, — все пустые. Они есть потому, что они есть на
любой файловой системе, где программу когда-либо запускали, и мир, заставляющий гостя создать
`/tmp` перед записью в него, отклонял бы открытие, которое удаётся везде.

**Каталог — это имя, а не вместилище.** Его можно создать, о нём можно спросить, его можно открыть
и синхронизировать, и файл нельзя создать там, где нет его каталога. Чем он не является — так это
шагом обхода: разрешение идёт по целому пути, поэтому нет ни ссылок, ни `..`, ни текущего каталога,
относительно которого что-то считалось бы. `getdents64` отвечает пусто, что бы там ни лежало.

`/dev/urandom` и `/dev/random` разрешаются и читаются как бесконечная выборка. **Под `/proc` и
`/sys` не существует ничего** — открытие отвечает `ENOENT`, что переносимая программа и так
обрабатывает, а программа, которой нужен такой путь, идёт тем путём, который держит для ядра, этого
не предлагающего. `statfs` и `fstatfs` сообщают об одном устройстве с личностью ext4, о размере
блока, который сообщает `stat` каждого файла, и о свободном месте, выведенном из того, что мир
действительно держит.

**Отображение файла моделируется** — хранилище держит свои страницы именно так, и чтение через окно
не то же самое, что чтение. Отображение, ни на что не опирающееся, пропускается и сюда не доходит:
проверка идёт по флагу `MAP_ANONYMOUS`, а не по дескриптору, потому что с этим флагом вызывающий
волен назвать любой дескриптор.

Вызов *подменяется*, а не отвечается: гость получает от хоста безымянную память — адресное
пространство принадлежит процессу, и вырастить его можно только позволив ему попросить, — а мир
пишет туда файл, когда вызов возвращается. Дальше две копии держатся в согласии, и куда течёт
истина, зависит от того, зачем отображение делали:

| | отображение только для чтения | отображение с записью |
|---|---|---|
| истина в файле | да | нет — в отображении |
| освежается | когда файл меняется под ним | никогда; оно и есть изменение |
| забирается обратно | никогда | при чтении файла и при `msync` |
| долговечно | всегда было | при `msync`, идущем тем же путём, что и `fsync` |

`msync` — точка долговечности, и выборки на ней те же, что на синхронизации: тот же отказ, та же
задержка. Гость, пишущий только через отображение, может потерять записи при крахе — ради этого всё
и моделируется, а не пропускается. Один `msync` поверх отображений нескольких файлов отклоняется:
синхронизация — одна операция с одной судьбой, а выборка на каждое отображение позволила бы живому
состоянию решать раскладку ленты.

Двух вещей здесь нет. **Отображение делается записываемым, о какой бы защите ни просили**, потому
что супервизор пишет через те же права страниц, что и гость, а отображение, в которое он не может
писать, — это отображение, которое он не может держать правдивым; поэтому гость, пишущий через
объявленное им же «только для чтения», здесь не падает, хотя ядро уронило бы его. Это дефект,
которого модель не ловит, и никогда — дефект, который она выдумывает. И `mremap` пропускается, так
что переехавшее им отображение *файла* теряется из виду; ничто из увиденного до сих пор их не
двигает.

## 5. Ожидания по скорости

Замедление относительно родного запуска, измеряемое как отношение на той же машине в том же джобе
([`TESTING.md`](./TESTING.md) §11). Цель T3 — не хуже 5×; ориентир — Hermit с 3–6×.

| Форма нагрузки | Ожидание | Почему |
|---|---:|---|
| вычислительная, мало системных вызовов | 1.2–2× | почти всё отсекает seccomp; платим только за точки переключения |
| набор тестов встраиваемой базы данных | 3–4× | измерено на `redb`: 20 000 перехваченных вызовов против 0.36 с работы |
| сбалансированная серверная нагрузка | 3–5× | цель, под которую оптимизируем |
| шторм системных вызовов (цикл `getpid`) | 400–600× | каждый вызов — остановка, а родной `getpid` — 70 нс; это нижняя граница перехвата, а не нагрузка |
| много потоков с высокой конкуренцией | 4–8× | сериализация плюс решение о переключении на каждой точке синхронизации |
| с измерением прогресса по счётчику переходов | +10–20% | одно чтение `perf_event_open` на точку переключения |
| со сбором покрытия | +5–15% | записи в разделяемую память внутри гостя |

**Число перехваченных вызовов** сообщается в сводке каждого прогона, а зависший прогон
дополнительно перечисляет вызовы, которые делал чаще всего. Перехват — это то, за что прогон
платит, поэтому скачок этого числа — самый быстрый способ диагностировать неожиданное замедление:
какой-то вызов переехал из пропускаемых в трассируемые, а это изменение таблицы, а не
проблема машины.

## 8. Как добавить платформу

Планка, по порядку:

1. `bohr doctor` даёт чистый проход на платформе;
2. наборы L3 и L4 проходят на CI-раннере этой платформы, а не на ноутбуке;
3. кросс-платформенное воспроизведение работает в обе стороны с уже поддержанной платформой
   ([`TESTING.md`](./TESTING.md) §7.3);
4. таблица скорости из §5 измерена, а не скопирована;
5. этот документ и матрица поддержки в README обновлены тем же изменением.

Шаги 3 и 4 — те, которые пропускают, и именно они имеют значение: платформа, на которой находки не
воспроизводятся кросс-платформенно, — это платформа, которая раскалывает пользователей на тех, кто
не может обмениваться баг-репортами.
